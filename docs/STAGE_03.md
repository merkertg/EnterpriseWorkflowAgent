## 1. Что делает этот этап

На этапе 02 счёт, заказ и процесс жили в памяти Python и исчезали после
завершения программы. Теперь они сохраняются в PostgreSQL. Важнее самого
сохранения — гарантии вокруг него:

| Вопрос | Ответ этапа 03 |
| --- | --- |
| Что будет, если запрос прервётся на середине? | Команда пишет все свои строки в одной транзакции: всё или ничего |
| Что, если два сотрудника меняют процесс одновременно? | Номер версии записи не даёт молча перезаписать чужое изменение |
| Что, если клиент повторит запрос из-за сбоя сети? | Ключ идемпотентности возвращает прежний результат без второго выполнения |
| Кто, когда и откуда изменил состояние? | Журнал аудита хранит команду, состояния, версии входов и источник |
| Изменили заказ после проверки — что стало со старой проверкой? | Она по-прежнему ссылается на прежнюю версию заказа и её хеш |

| Уже реализовано | Когда появится остальное |
| --- | --- |
| PostgreSQL, SQLAlchemy, миграции Alembic | Загрузка файлов и извлечение полей — этап 04 |
| Неизменяемые версии счёта, заказа и политики с SHA-256 | Полная сверка позиций и пометка устаревших результатов — этап 05 |
| Транзакции, аудит, оптимистическая блокировка, идемпотентность | Пользователи, роли, HTTP-команды и outbox — этап 06 ([реализовано](STAGE_06.md)) |
| Демонстрация на PostgreSQL и интеграционные тесты | Docker compose и резервное копирование — этап 10 |

HTTP API по-прежнему содержит только `/health`. Команды доступны как
Python-функции сервиса и через учебную командную строку.

## 2. Слои и направление зависимостей

```text
app/domain/          Правила и переходы. Только стандартная библиотека.
    ↑
app/application/     Сценарии команд, транзакция, аудит, идемпотентность.
    ↑                Знает о «хранилище» только через протоколы (порты).
app/infrastructure/  SQLAlchemy-модели таблиц и репозиторий PostgreSQL.
migrations/          Alembic-миграции схемы.
```

**Порт** — описание того, что нужно сценарию от хранилища, без деталей
реализации. Здесь это протоколы `WorkflowRepository` и `UnitOfWork`
в `app/application/ports.py`. **Адаптер** — реализация порта для конкретной
технологии: `SqlAlchemyWorkflowRepository` в `app/infrastructure/db/`.

**Unit of Work** («единица работы») — одна транзакция. Сценарий открывает её
блоком `with`, выполняет записи и явно вызывает `commit()`. Если блок
завершился без `commit()` или с исключением, всё откатывается.

Тест `tests/test_architecture.py` проверяет, что `app/domain` и
`app/application` не импортируют FastAPI, Pydantic, SQLAlchemy, Alembic и
psycopg. Домен по-прежнему решает каждый переход; база данных хранит
результат, а не определяет правила.

## 3. Подготовка PostgreSQL

Нужен PostgreSQL (проверено на версии 18.3) и две пустые базы:
для разработки и для тестов. Имя тестовой базы обязано оканчиваться на `_test`.

Вариант с уже установленным PostgreSQL (имя роли и пароль выбери свои):

```bash
createuser --pwprompt enterprise_workflow
createdb --owner enterprise_workflow enterprise_workflow
createdb --owner enterprise_workflow enterprise_workflow_test
```

Вариант с Docker (в проверке этапа эта команда не запускалась; приводится как
пример):

```bash
docker run --name enterprise-workflow-db -d -p 127.0.0.1:5432:5432 -e POSTGRES_USER=enterprise_workflow -e POSTGRES_PASSWORD=change-me -e POSTGRES_DB=enterprise_workflow postgres:18.3
```

Тестовую базу во втором варианте создай отдельно, например через
`docker exec enterprise-workflow-db createdb -U enterprise_workflow enterprise_workflow_test`.

Адрес подключения задаётся переменной `DATABASE_URL`, например в своём `.env`:

```text
DATABASE_URL=postgresql+psycopg://enterprise_workflow:ПАРОЛЬ@127.0.0.1:5432/enterprise_workflow
```

Префикс `postgresql+psycopg://` обязателен: проект использует драйвер psycopg 3.
Настройка хранится как `SecretStr`, поэтому пароль не появляется при печати
объекта настроек. Файл `.env` не коммитится.

## 4. Миграции Alembic

**Миграция** — версия схемы базы данных в виде кода. Она позволяет одинаково
создать таблицы на любом компьютере и в CI.

```bash
uv run --locked alembic upgrade head
uv run --locked alembic current
uv run --locked alembic check
```

`upgrade head` применяет все ревизии. `current` показывает версию схемы.
`check` сравнивает схему с SQLAlchemy-моделями и сообщает
`No new upgrade operations detected`, если расхождений нет.
`uv run --locked alembic upgrade head --sql` печатает SQL без подключения
к базе — удобно, чтобы прочитать, что именно будет создано.

`alembic downgrade base` удаляет все таблицы этапа вместе с данными. Не
выполняй его на базе, данные которой нужны.

Первая ревизия `migrations/versions/0001_stage03_persistence.py` была получена
автогенерацией и проверена вручную. Две ручные правки:

1. Ссылка `workflows.last_snapshot_id → validation_snapshots.id` добавляется
   после создания обеих таблиц: таблицы ссылаются друг на друга.
2. Для таблиц истории создаётся триггер, запрещающий `UPDATE` и `DELETE`.

Применённую миграцию не редактируют. Изменение схемы — новая ревизия.

## 5. Таблицы

| Таблица | Что хранит | Меняется? |
| --- | --- | --- |
| `invoice_versions`, `invoice_version_lines` | Версия счёта и её позиции | Нет |
| `purchase_order_versions`, `purchase_order_version_lines` | Версия заказа и её позиции | Нет |
| `policy_versions` | Версия политики проверки | Нет |
| `workflows` | Текущее состояние, номер версии записи, закреплённые версии входов | Да |
| `validation_snapshots` | Результат каждой проверки со ссылками и хешами входов | Нет |
| `audit_events` | Журнал изменений состояния | Нет |
| `idempotency_records` | Результат команды по ключу идемпотентности | Нет |

Деньги хранятся в `NUMERIC(14, 2)`, количество — в `NUMERIC(12, 6)`. Это
точные десятичные типы: драйвер возвращает Python `Decimal`, без `float`.
Ограничения `CHECK` повторяют ключевые правила домена: валюта из списка,
сумма неотрицательна, количество положительно, номер версии больше нуля.
Это вторая линия защиты от ручного SQL; основная проверка остаётся в домене.

## 6. Неизменяемые версии и хеш содержимого

`WorkflowService.record_purchase_order(order)` сохраняет заказ как **версию**:

- Если содержимое совпадает с последней версией этого заказа, возвращается
  она же — новая строка не создаётся.
- Если отличается, создаётся следующая версия: 1, 2, 3…
- Возврат к прежнему содержимому (A → B → A) создаёт версию 3: история правок
  сохраняется полностью.

Так же работают `record_invoice()` и `record_policy()`. Каждая версия получает
**хеш содержимого** — SHA-256 от канонического JSON. «Канонический» означает
однозначный: ключи отсортированы, лишних пробелов нет, суммы записаны строками
(`"12.50"`, `"2.000000"`), есть метка схемы (`"schema":"purchase_order.v1"`).
Одинаковое содержимое всегда даёт одинаковый хеш; изменение любого делового
поля — другой хеш. Реализация: `app/domain/content_hash.py`.

При каждом чтении версия собирается в доменный объект и хеш вычисляется
заново. Если строку изменили в обход приложения (тест отключает триггер и
меняет количество), чтение завершится ошибкой `StoredDataIntegrityError`,
а не вернёт изменённые данные как исходные.

Хеш политики покрывает её **данные** (идентификатор и список валют), но не
Python-код правил. Если меняется логика проверки, нужен новый `policy_id`,
например `basic-demo-v2`. Сохранённый результат старой логики при загрузке
процесса будет отклонён как не совпадающий с текущими правилами.

## 7. Команда как одна транзакция

Команды сервиса: `start`, `check`, `approve`, `reject`, `revise`. Каждая
выполняется в одной транзакции в таком порядке:

```text
1. Найти ключ идемпотентности. Есть → вернуть прежний результат.
2. Загрузить процесс и сравнить его версию с expected_version.
3. Вычислить новый доменный снимок (чистая функция этапа 02).
4. Записать ключ идемпотентности с результатом.
5. Записать снимок проверки (только для check).
6. Обновить строку workflows: UPDATE ... WHERE version = expected_version.
7. Записать событие аудита.
8. COMMIT.
```

Если любой шаг падает, `COMMIT` не выполняется и PostgreSQL откатывает все
предыдущие записи. Тест `test_failure_before_commit_leaves_no_partial_state`
искусственно ломает шаг 7 и проверяет, что в таблицах не осталось ни ключа,
ни снимка, ни новой версии процесса.

Процесс закрепляет **конкретные версии** входов: `start` и `revise` принимают
идентификаторы версий счёта, заказа и политики. `check` проверяет именно
закреплённые версии. Новая версия заказа сама по себе не меняет процесс:
чтобы проверить счёт по ней, нужна команда `revise`.

## 8. Оптимистическая блокировка

У строки `workflows` есть поле `version`. Каждая успешная команда увеличивает
его на 1. Команда, кроме `start`, принимает `expected_version` — версию,
которую видел вызывающий код:

```python
service.check("WF-1", expected_version=1, context=CommandContext("key-1", "cli"))
```

Если текущая версия другая, команда завершается `VersionConflictError`
(код `version_conflict`) и ничего не меняет. Это защищает от **потерянного
обновления**: ситуации, когда второй сотрудник, открывший старую версию,
незаметно перезаписывает решение первого.

Проверка выполняется дважды. Сначала сервис сравнивает версии после чтения —
это понятная ранняя ошибка. Затем само обновление выполняется условно:
`UPDATE ... WHERE version = :expected`. Если между чтением и записью другая
транзакция успела зафиксировать изменение, обновится ноль строк, и команда
тоже получит конфликт. Тест `test_compare_and_set_blocks_a_lost_update`
проверяет именно второй барьер.

«Оптимистическая» означает, что строка не блокируется заранее на время
раздумий пользователя: конфликт обнаруживается при записи.

## 9. Идемпотентность

**Идемпотентная** операция при повторе даёт тот же результат, что и при первом
выполнении. Каждая команда получает `CommandContext(idempotency_key, source)`.
Ключ выбирает вызывающий код: один ключ — одно намерение пользователя
(удобно использовать UUID).

| Ситуация | Результат |
| --- | --- |
| Новый ключ | Команда выполняется; результат сохраняется вместе с ключом |
| Тот же ключ, та же команда и аргументы | Возвращается сохранённый результат с `replayed=True`; новых строк нет |
| Тот же ключ, другая команда или аргументы | `IdempotencyKeyReusedError` (`idempotency_key_reused`) |
| Команда завершилась ошибкой | Ключ не сохраняется; можно повторить с исправленным запросом |

«Аргументы» сравниваются через **отпечаток запроса** — SHA-256 от команды,
идентификатора процесса, `expected_version` и остальных аргументов. Поле
`source` в отпечаток не входит: это метка происхождения, а не смысл запроса.

Повтор возвращает **исходный** результат, даже если процесс с тех пор ушёл
дальше. Клиент, потерявший ответ из-за сбоя сети, узнаёт, что его команда
уже выполнена, а не получает конфликт.

### Одновременные дубликаты

Два одинаковых запроса могут прийти почти одновременно. Ключ записывается
в начале записи (шаг 4), поэтому второй запрос ждёт первую транзакцию на
уникальном ключе. После её фиксации он получает нарушение уникальности,
повторяет поиск ключа и возвращает сохранённый результат.

При тестировании нашлась ещё одна гонка: второй запрос не нашёл ключ (шаг 1),
затем первый успел зафиксироваться, и второй прочитал уже версию 2 (шаг 2).
Без обработки он получил бы `version_conflict`, хотя это повтор. Теперь после
конфликта сервис ещё раз ищет ключ в новой транзакции и отвечает повтором.
Этот порядок событий воспроизводится детерминированно в
`test_duplicate_committed_between_lookup_and_read_is_replayed`.

## 10. Журнал аудита

Каждая успешная команда добавляет строку в `audit_events`:

| Поле | Смысл |
| --- | --- |
| `id`, `occurred_at` | Порядковый номер и время транзакции из PostgreSQL |
| `command`, `previous_state`, `new_state`, `workflow_version` | Что произошло |
| `invoice_version_id`, `purchase_order_version_id`, `policy_version_id` | Какие версии входов использовались |
| `snapshot_id`, `issue_codes` | Результат проверки — только коды причин |
| `actor_id`, `source`, `idempotency_key` | Кто и откуда выполнил команду |

Текст позиций, описания и причины решения в журнал не копируются. Тест
проверяет, что описания позиций счёта не встречаются в строках аудита.

`actor_id` и `source` передаёт вызывающий код. На этапе 03 нет входа в систему,
поэтому это заявленные, а не подтверждённые значения. Проверка личности и
ролей появилась на [этапе 06](STAGE_06.md).

Аудит, как и версии, защищён триггером от изменения и удаления. Пользователь
базы данных с правами владельца может отключить триггер — это защита от
ошибок и случайных правок, а не от администратора.

## 11. Снимок проверки и прежние версии входов

`check` сохраняет `validation_snapshots`: идентификаторы версий счёта, заказа
и политики, их хеши, рассчитанный итог и найденные причины. Сценарий из теста
`test_old_snapshot_keeps_original_inputs_after_order_and_policy_change`:

```text
check  → снимок S1: заказ v1 (итог 30.00), политика v1, причин нет
record → заказ v2 (итог 17.50), политика v2 (только USD)
revise → процесс закреплён за v2, состояние received
check  → снимок S2: заказ v2, политика v2, purchase_order_total_exceeded
```

После этого S1 по-прежнему загружается с заказом v1, итогом `30.00` и теми же
хешами. Новая версия ничего не перезаписала.

Чего этап 03 ещё **не** делает: не сообщает, что для закреплённого заказа
появилась более новая версия, и не запрещает одобрение в такой ситуации.
Пометка устаревших результатов — задача этапа 05, проверка применимости
версий в транзакции согласования — [этапа 06](STAGE_06.md).

## 12. Демонстрация

```bash
uv run --locked alembic upgrade head
uv run --locked python -m app.persistence_demo
```

Команда создаёт вымышленные документы с уникальными идентификаторами запуска
и выводит JSON. Сценарий: `start` → `check` → повтор `check` с тем же ключом
(`replayed: true`) → `approve` по устаревшей версии (`version_conflict`) →
новые версии заказа и политики → `revise` → `check` (`needs_review`) →
`reject`. В конце печатаются оба снимка и журнал аудита.

Скопируй `workflow_id` из вывода и прочитай процесс в новом процессе Python:

```bash
uv run --locked python -m app.persistence_demo show DEMO-WF-xxxxxxxxxxxx
```

Данные читаются из базы, а не из памяти предыдущего запуска. Можно
перезапустить сам сервер PostgreSQL и повторить `show` — результат не
изменится. Без `DATABASE_URL` команда завершается с кодом 2 и пояснением,
без схемы — подсказкой выполнить `alembic upgrade head`.

## 14. Как проверять этап

Базовые проверки не требуют базы данных:

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts migrations
uv run --locked pytest
uv run --locked python scripts/check_docs.py
```

Без `TEST_DATABASE_URL` интеграционные тесты PostgreSQL помечаются как
пропущенные (`skipped`). Чтобы они выполнились, задай переменную окружения
процесса (не `.env`):

```bash
TEST_DATABASE_URL=postgresql+psycopg://enterprise_workflow:ПАРОЛЬ@127.0.0.1:5432/enterprise_workflow_test uv run --locked pytest
```

Тесты удаляют и заново создают схему этой базы, поэтому имя обязано
оканчиваться на `_test`; иначе они остановятся с ошибкой. Перед каждым тестом
таблицы очищаются. `REQUIRE_TEST_DATABASE=1` превращает пропуск в ошибку —
так настроен CI, чтобы потерянная настройка не выглядела как успех.
Только тесты базы: `pytest -m postgres`; только быстрые: `pytest -m "not postgres"`.

Что проверяют интеграционные тесты: воспроизводимость миграций и совпадение
схемы с моделями, типы `NUMERIC`, триггеры истории, ограничения `CHECK`,
версии и хеши, обнаружение изменённой строки, транзакционность, конфликты
версий, повтор и повторное использование ключа, одновременные дубликаты и
одновременные разные команды, сохранность старых снимков, чтение новым
пулом соединений и запуск демонстрации в отдельных процессах.

Фактические результаты — в [VERIFICATION.md](VERIFICATION.md).

## 15. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| `Set DATABASE_URL ...` | Задай `DATABASE_URL` в окружении или в `.env` |
| `Database URL must use the postgresql+psycopg:// driver` | Замени `postgresql://` на `postgresql+psycopg://` |
| `relation "workflows" does not exist` / подсказка про схему | Выполни `uv run --locked alembic upgrade head` |
| Все тесты `tests/persistence` пропущены | Не задан `TEST_DATABASE_URL` в окружении процесса |
| `The test database name must end with _test` | Защита от удаления данных разработки: создай отдельную базу `..._test` |
| `version_conflict` | Процесс изменился после чтения: прочитай текущую версию и реши заново |
| `idempotency_key_reused` | Для нового намерения нужен новый ключ |
| `stored_data_integrity` | Строка изменена в обход приложения или изменилась логика правил |
| `table ... is append-only` | Историю нельзя менять; создай новую версию |
| Новая версия заказа не повлияла на процесс | Процесс закреплён за версиями; используй `revise` |
