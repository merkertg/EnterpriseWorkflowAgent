## 1. Что делает этот этап

Последний этап превращает учебный проект в **воспроизводимый выпуск
`0.10.0`**: тот же код и те же версии пакетов поднимаются одной командой на
другой машине.

- `Dockerfile` собирает два образа из `uv.lock`. Базовые образы закреплены по
  digest, процессы работают от непривилегированного пользователя.
- `compose.yaml` поднимает PostgreSQL, миграции, API, получатель webhook с
  обработчиком outbox и страницу. Порты открыты только на `127.0.0.1`.
- `python -m app.smoke` проходит весь сценарий по HTTP против запущенного
  стека: вход, загрузка, запуск, проверка, сверка, одобрение, доставка.
- `python -m app.backup` выгружает учебные данные и загружает их в пустую
  базу. Результат сверяется с манифестом до `COMMIT`.
- В CI появились два задания: набор оценок с отчётом-артефактом и стек
  compose со smoke-проверкой и циклом резервной копии.
- [LIMITATIONS.md](LIMITATIONS.md) собирает все ограничения проекта в одном
  месте.

| Вопрос | Ответ этапа 10 |
| --- | --- |
| Что нужно, чтобы поднять всё? | Docker с Compose и два секрета в окружении |
| Откуда версии пакетов? | Только из `uv.lock` (`uv sync --locked`) |
| Почему образы не «плывут»? | Python, uv и PostgreSQL закреплены по digest |
| Где хранятся пароли? | Нигде в репозитории: compose требует их из окружения |
| Кто может открыть сервисы? | Только этот компьютер: порты на `127.0.0.1` |
| Как проверить, что стек работает? | `app.smoke` проходит сценарий и ждёт доставки |
| Как сохранить и вернуть данные? | `app.backup export`, затем `restore` в пустую базу и `verify` |
| Это промышленный deploy? | Нет: публикация образов и развёртывание вне объёма |

| Реализовано | Вне объёма |
| --- | --- |
| Образы `app` и `ui`, compose, smoke-проверка | Публикация образов в реестр, TLS, развёртывание |
| Логическая резервная копия с проверкой | Резервирование по расписанию, шифрование копий |

## 2. Как запустить стек

Нужен Docker с Compose v2. Команды ниже используют OpenSSL для генерации
секретов. Вместо генерации можно вручную задать два независимых случайных
значения длиной не меньше 32 символов. Python и uv на основной машине
для контейнерного стека не нужны.

```bash
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export SANDBOX_WEBHOOK_SECRET="$(openssl rand -hex 24)"
docker compose up -d --build --wait
docker compose run --rm --no-deps api python -m app.smoke --api http://api:8003
docker compose run --rm --no-deps api python -m app.ui_demo_setup
```

После этого API отвечает на `http://127.0.0.1:8003`, страница — на
`http://127.0.0.1:8501`. Токены для страницы печатает `ui_demo_setup`.
`docker compose down` останавливает стек и сохраняет данные;
`docker compose down -v` удаляет и тома.

| Сервис | Образ | Что делает |
| --- | --- | --- |
| `postgres` | `postgres:18.3@sha256:…` (тот же, что в CI) | База; том `pgdata` |
| `migrate` | `app` | `alembic upgrade head` и завершается |
| `api` | `app` | Uvicorn на 8003; проверка здоровья по `/health` |
| `receiver` | `app` | Получатель webhook на `127.0.0.1:8010` внутри своего сетевого пространства |
| `worker` | `app` | Обработчик outbox в **сетевом пространстве `receiver`** |
| `ui` | `ui` | Streamlit на 8501; ходит в API по `http://api:8003` |

Почему `worker` живёт в сетевом пространстве получателя? Этап 09 требует,
чтобы адрес доставки был `127.0.0.1` или `[::1]`. В compose у каждого
контейнера свой loopback. Общее сетевое пространство сохраняет правило
«только loopback» без исключений для контейнеров.

## 3. Образы

```text
uv (digest) ─┐
python:3.12.15-slim (digest) → build: uv sync --locked --no-dev
                             → build-ui: + группа ui
runtime: пользователь app (uid 10001), код app/ ui/ sandbox/ migrations/
  ├─ target app: /opt/venv из build     (312 МБ)
  └─ target ui:  /opt/venv из build-ui  (880 МБ: Streamlit тянет pandas и pyarrow)
```

- В образ не попадают `.git`, `.env`, `var/`, `.venv`, документация и тесты
  (`.dockerignore`).
- Секретов в образе нет: `DATABASE_URL` и секрет webhook приходят из
  окружения при запуске.
- `UV_PYTHON_DOWNLOADS=never`: используется Python образа, uv его не
  скачивает.

## 4. Smoke-проверка

`python -m app.smoke --api URL [--wait 60]` готовит вымышленных сотрудников и
справочники через `DATABASE_URL` (как `app.ui_demo_setup`), а дальше
работает как обычный клиент HTTP — тем же клиентом, что страница:

| Шаг | Ожидается |
| --- | --- |
| `GET /health` | `ok` |
| Вход специалиста | `ui-clerk` |
| Загрузка образца | извлечение `complete` |
| Запуск | `received` |
| Базовая проверка | `awaiting_approval` |
| Сверка | `matched` |
| Одобрение утверждающим | `approved` |
| Ожидание доставки | `delivered` (с `--wait 0` шаг пропускается) |

Отчёт печатается в JSON, код завершения 0 только если совпали все шаги.

## 5. Резервная копия и восстановление

Для команд ниже нужен `DATABASE_URL`: при выгрузке — исходная база,
при восстановлении — пустая целевая база той же ревизии. Для `verify` и
`check` оставь подключение к восстановленной базе.

```bash
uv run --locked python -m app.backup export var/backups/before-lesson
uv run --locked python -m app.backup verify var/backups/before-lesson
uv run --locked python -m app.backup restore var/backups/before-lesson   # в пустую базу
uv run --locked python -m app.backup check
```

Копия охватывает таблицы PostgreSQL. Формат — каталог: по одному файлу
JSON Lines на таблицу и `manifest.json`.

- **Выгрузка.**
  - Все таблицы читаются в одной транзакции `REPEATABLE READ`, то есть в
    один момент времени.
  - Строки упорядочены по первичному ключу, JSON канонический.
  - Время приводится к UTC, поэтому копии с серверов в разных часовых поясах
    хешируются одинаково.
  - Каталог создаётся с правами 700, файлы — с правами 600.
  - В манифесте — версия формата и приложения, ревизия Alembic, число строк
    и SHA-256 каждого файла.
- **Восстановление.** Каталог читается, хеши файлов сверяются. База должна
  быть на той же ревизии и **пустой**. Затем всё выполняется в одной
  транзакции:
  1. Таблицы вставляются от родителей к детям.
  2. Для `audit_events` используется `OVERRIDING SYSTEM VALUE`, после чего
     последовательность сдвигается за восстановленные значения.
  3. Восстановленная база тут же выгружается в память и сравнивается с
     манифестом. Любое расхождение откатывает всё.
- **Цикл ключей.** `workflows` ссылается на последний снимок проверки и на
  снимок сверки решения, а снимки — на `workflows`. Поэтому эти два
  столбца сначала вставляются пустыми и заполняются, когда все таблицы
  загружены. Функция `late_columns()` находит такие ключи по схеме. Если
  цикл когда-нибудь пройдёт через таблицу только для добавления или
  обязательный столбец, восстановление откажет заранее.
- **`verify`** сравнивает живую базу с копией по таблицам. **`check`**
  перечитывает все процессы (хеши версий), байты документов и повторяет
  каждую сверку.

На этих данных цикл нашёл настоящую ошибку: первая версия восстановления
падала на внешнем ключе `workflows.last_snapshot_id`. Отсюда отложенные
столбцы.

Копия содержит байты документов, сотрудников и хеши токенов. Даже с
вымышленными данными она хранится в `var/` и в Git не попадает. Манифест
защищает от порчи файлов, но не от намеренной подмены: копия не подписана.

SQLite получателя webhook в эту копию не входит. Его том нужно сохранять
отдельно: общей атомарной копии PostgreSQL и получателя нет. В цикле
восстановления CI том получателя сохраняется, а заново создаётся только
том PostgreSQL. `docker compose down -v` удаляет оба тома, поэтому это
команда полного сброса, а не обычный шаг восстановления PostgreSQL.

## 6. CI

| Задание | Что проверяет |
| --- | --- |
| `checks` | Ruff, формат, mypy, миграции, `alembic check`, все тесты с PostgreSQL, ссылки |
| `evaluations` | `python -m app.evals run` на отдельной базе; отчёт — артефакт на 14 дней |
| `compose` | Сборка образов, стек с проверками здоровья, smoke, цикл «выгрузить → пересоздать PostgreSQL → восстановить → сверить → проверить» с сохранением тома получателя |

Секреты для `compose` создаются случайно на каждый запуск и маскируются в
журнале. Действия GitHub закреплены по SHA. Файл workflow — не
доказательство успешного запуска: удалённый CI отмечен как не подтверждённый.

## 7. Три вида свидетельств

| Вид | Статус |
| --- | --- |
| Локальные проверки | Выполнены и записаны в [VERIFICATION.md](VERIFICATION.md) |
| Настоящий провайдер модели | **Не проверялся**: адаптера нет, работают только детерминированные провайдеры |
| Удалённый CI | **Не подтверждён**: результаты запусков на GitHub не просматривались |

## 9. Как проверять этап

```bash
uv run --locked --group ui pytest tests/test_release_files.py
TEST_DATABASE_URL=… uv run --locked --group ui pytest tests/persistence/test_backup.py tests/persistence/test_smoke.py
docker compose up -d --build --wait
docker compose run --rm --no-deps api python -m app.smoke --api http://api:8003
```

`tests/test_release_files.py` без Docker проверяет обещания файлов выпуска:

- базовые образы закреплены по digest;
- пользователь не root;
- порты только на `127.0.0.1`, а секреты обязательны и в файлах не лежат;
- образ PostgreSQL совпадает с образом CI;
- `.dockerignore` не пускает в сборку секреты и локальные данные;
- версии совпадают.

## 10. Ограничения

Полный список — в [LIMITATIONS.md](LIMITATIONS.md). Для этого этапа:

- образы проверены только на macOS (Docker Desktop, arm64); сборка на amd64
  — задача CI, который не подтверждён;
- нет HTTPS, публикации образов, обновления без остановки и мониторинга;
- копия логическая и не подписана; восстановление только в пустую базу той
  же ревизии; резервирования по расписанию нет;
- SQLite получателя не включён в копию; атомарного резервирования двух
  хранилищ нет;
- образ `ui` большой (880 МБ) из-за зависимостей Streamlit.

## 11. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| `required variable POSTGRES_PASSWORD is missing` | Задай `POSTGRES_PASSWORD` и `SANDBOX_WEBHOOK_SECRET` |
| `Cannot connect to the Docker daemon` | Запусти Docker Desktop или службу Docker |
| `backup_error: Restore needs an empty database` | Используй пустую базу той же ревизии; при пересоздании PostgreSQL сохрани том получателя |
| `backup_error: … revision` | Приведи базу к ревизии копии через Alembic |
| `backup_error: … SHA-256` | Файл копии изменён или повреждён; возьми другую копию |
| Порт 8003 или 8501 занят | Останови локальный `uvicorn`/Streamlit или другой стек |
