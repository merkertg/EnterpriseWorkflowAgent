# Этап 05. Детерминированная сверка счёта с заказом

[README](../README.md) · [Дорожная карта](ROADMAP.md) ·
[Проверка](VERIFICATION.md) ·
[Краткая инструкция на английском](instructions/reconciliation.md) ·
[ADR 0005](adr/0005-deterministic-reconciliation.md)

## 1. Что делает этот этап

Базовые правила этапа 02 сравнивали только итоги и заголовок. Совпадение
итогов не доказывает совпадение позиций: можно выставить другой товар на ту
же сумму. Этап 05 сверяет счёт с заказом построчно — по SKU, количеству и
цене — под явной **версией правил** с допусками.

| Вопрос | Ответ этапа 05 |
| --- | --- |
| Какую разницу в цене можно простить? | Ту, что указана в версии правил для валюты, например 0.05 USD на единицу |
| Что, если для валюты правил нет? | `no_rule_for_currency`: автоматического продвижения нет |
| Откуда видно, почему расхождение? | Код, ожидаемое и найденное значение, сработавшее правило и цитата из документа |
| Что, если тот же счёт прислали дважды? | `duplicate_invoice` со ссылкой на другой процесс |
| Что, если заказ или правила изменились после сверки? | Снимок помечается устаревшим и требует новой сверки |
| Можно ли проверить старый результат? | Да: снимок пересчитывается из своих версий и даёт тот же результат |

| Уже реализовано | Когда появится остальное |
| --- | --- |
| Версии правил сверки с допусками и округлением | Одобрение только по свежему чистому снимку — этап 06 |
| Построчная сверка, повторный счёт, отчёт с источниками | Вход сотрудника и роли — этап 06 |
| Неизменяемые снимки, устаревание, воспроизведение | Модель, объясняющая расхождения, — этап 07 |
| Командная строка и демонстрация | Интерфейс — этап 08 |

Все суммы считает обычный код на `Decimal`. Модель (этап 07) не вычисляет
итоги и не решает, есть ли расхождение.

## 2. Правила сверки — отдельная версия

```text
ReconciliationRules(
    rules_id="demo-rules",
    currency_rules=(
        CurrencyRule(Currency.USD, unit_price_tolerance=Money("0.05"), total_tolerance=Money("0.10")),
        CurrencyRule(Currency.EUR, ...),
    ),
    allow_partial_quantities=True,
    require_source_document=True,
)
```

(В коде суммы создаются как `Money(Decimal("0.05"), Currency.USD)`; здесь
запись сокращена.)

| Параметр | Смысл |
| --- | --- |
| `unit_price_tolerance` | Насколько цена единицы может отличаться от цены заказа |
| `total_tolerance` | Допуск для итогов: заявленного и суммы сопоставленных строк |
| `decimal_places`, `rounding` | Записаны явно: 2 знака и `ROUND_HALF_UP` — единственное, что реализует денежный модуль; другое значение отклоняется |
| `allow_partial_quantities` | Можно ли выставлять меньше заказанного |
| `require_source_document` | Требовать ли, чтобы счёт пришёл из полного извлечения документа |

Правила хранятся версиями, как заказ и политика на этапе 03:
`ReconciliationService.record_rules()` возвращает ту же версию для того же
содержимого и следующую — для изменённого. Хеш не зависит от порядка правил
валют: они сортируются. Таблицы `reconciliation_rule_versions` и
`reconciliation_currency_rules` (миграция `0003`) защищены триггером, а
`CHECK` запрещает неподдерживаемое округление и отрицательные допуски.

Допуск включительный: разница ровно 0.05 при допуске 0.05 проходит, 0.06 — нет.

## 3. Что сравнивается

| Код | Когда |
| --- | --- |
| `missing_source_document` | Правила требуют документ, а счёт создан кодом |
| `duplicate_invoice` | Есть другой открытый или одобренный процесс с тем же поставщиком и номером счёта |
| `no_rule_for_currency` | В правилах нет валюты счёта — цены и итоги не оцениваются |
| `missing_purchase_order` | Заказа нет — сравнивать не с чем |
| `purchase_order_reference_mismatch` | Счёт ссылается на другой заказ |
| `supplier_mismatch` | Поставщики различаются |
| `currency_mismatch` | Валюты различаются — суммы не сравниваются, конвертации нет |
| `unknown_line` | SKU счёта нет в заказе |
| `quantity_exceeds_order` | Выставлено больше, чем заказано |
| `quantity_below_order` | Меньше заказанного, а частичное выставление запрещено |
| `unit_price_mismatch` | Цена отличается больше допуска на единицу |
| `declared_total_mismatch` | Заявленный итог отличается от суммы строк больше допуска |
| `expected_total_mismatch` | Сопоставленные строки отличаются от цен заказа больше допуска на итог |

Причины перечисляются в стабильном порядке таблицы; все найденные возвращаются
сразу. Нет причин — статус `matched`; есть — `needs_review`. `matched` не
означает одобрение: решение по-прежнему за сотрудником.

### Почему нужен допуск на итог

Пусть допуск на единицу 0.05 USD, на итог 0.10 USD. Уплотнитель стоит в
заказе 12.50, в счёте 12.54 — разница 0.04 в пределах допуска. Фильтр 5.00 и
5.04 — тоже в пределах. Но уплотнителей два: 2 × 0.04 + 0.04 = 0.12 > 0.10.
Каждая строка «почти верна», а вместе поставщик получил бы на 0.12 больше.
`expected_total_mismatch` ловит такое накопление и цитирует цены всех
строк, которые отличаются от заказа.

### Ожидаемая сумма и округление

Ожидаемая сумма строки = цена из заказа × выставленное количество,
округлённая один раз по `ROUND_HALF_UP` до 2 знаков, как и строки счёта.
Например, 0.01 × 0.5 = 0.005 → 0.01 с обеих сторон, расхождения нет.
Строки с неизвестным SKU в ожидаемую сумму не входят: они уже отмечены
`unknown_line`, и та же сумма не должна попадать в отчёт дважды.

## 4. Отчёт: код, значения, правило, источник

Каждое расхождение (`Discrepancy`) содержит:

| Поле | Пример |
| --- | --- |
| `code` | `unit_price_mismatch` |
| `field` | `lines[2].unit_price` — имя из схемы полей этапа 04 |
| `expected` | `5.00 USD ± 0.05` |
| `actual` | `5.10 USD` |
| `rule` | `USD.unit_price_tolerance=0.05` |
| `sources` | страница и диапазон символов в документе |

Источник берётся из извлечения, которое создало версию счёта. Отчёт
(`ReconciliationService.report`) превращает его в цитату:

```json
{"code": "unit_price_mismatch", "field": "lines[2].unit_price",
 "expected": "5.00 USD ± 0.05", "actual": "5.10 USD",
 "rule": "USD.unit_price_tolerance=0.05",
 "sources": [{"page": 1, "line_number": 7, "quote": "5.10"}]}
```

Если один счёт пришёл несколькими файлами (TXT и PDF), используется самое
раннее полное извлечение, и его идентификатор записывается в снимок.

## 5. Снимок сверки

`reconcile(workflow_id, rules_version_id=...)` сверяет **закреплённые** в
процессе версии счёта и заказа и сохраняет неизменяемую строку
`reconciliation_snapshots`:

- версии и хеши счёта, заказа и правил;
- исходный документ и его SHA-256;
- извлечение и хеш его полей вместе с цитатами («использованные поля»);
- список процессов-дубликатов на момент сверки;
- версия логики `reconciliation.v1`;
- итоги, сравнение строк и расхождения.

Из всего перечисленного вычисляется **хеш входов**. Повторная сверка с тем
же хешем возвращает существующий снимок и ничего не пишет; одновременные
одинаковые запросы приводят к одной строке (уникальный ключ
процесс + хеш входов).

Сверка не меняет состояние процесса и не пишет событие аудита: снимок сам
является неизменяемой записью со временем и всеми входами. Связь снимка с
решением сотрудника появится на этапе 06.

## 6. Устаревание и воспроизведение

`freshness(snapshot_id)` сравнивает входы снимка с тем, что применимо сейчас:

| Причина | Когда |
| --- | --- |
| `workflow_inputs_changed` | Процесс после `revise` закреплён за другими версиями |
| `purchase_order_changed` | У заказа появилась более новая версия |
| `purchase_order_available` | Заказа не было, а теперь он записан |
| `rules_changed` | У набора правил появилась новая версия |
| `duplicates_changed` | Изменился список процессов с тем же счётом |

Устаревший снимок не исправляется — он остаётся историей. Нужна новая
сверка: при изменённом заказе сначала `revise` процесса на новую версию, затем
`check` и `reconcile`.

`reproduce(snapshot_id)` пересчитывает результат из версий **самого снимка**,
а не из последних: загружает счёт, заказ, правила и извлечение по их
идентификаторам, проверяет хеши и запускает ту же функцию. Результат обязан
совпасть с сохранённым. Если строку правил изменить в обход приложения, хеш
не совпадёт и воспроизведение завершится `stored_data_integrity`.

## 7. Повторный счёт

Дубликатом считается другой процесс в состоянии, отличном от `rejected`, со
счётом того же поставщика и с тем же номером. Пример: тот же файл прислали
второй раз и для него запустили новый процесс. Второй процесс получает
`duplicate_invoice` со ссылкой на первый. У снимка первого процесса
появляется причина устаревания `duplicates_changed`. После отклонения
дубликата (`reject`) снимок первого снова актуален.

Другие виды повторов — тот же счёт под новым номером или с другим
поставщиком — эта проверка не ловит.

## 8. Демонстрация

```bash
uv run --locked alembic upgrade head
uv run --locked python -m app.reconciliation_cli demo
uv run --locked python -m app.reconciliation_cli show SNAPSHOT_ID
```

Номера документов, заказа и правил содержат идентификатор запуска, поэтому
повторный запуск не считает прошлые процессы дубликатами. Сценарий:

| Шаг | Результат |
| --- | --- |
| A: счёт точно по заказу | `matched` |
| B: цены 12.54 и 5.10 | `unit_price_mismatch` для фильтра и `expected_total_mismatch` с цитатами обеих цен |
| C: 3 фильтра вместо 1 и лишняя прокладка | `quantity_exceeds_order` и `unknown_line` |
| D: счёт A прислан ещё раз | `duplicate_invoice` со ссылкой на A |
| Новые версии правил и заказа | Снимок A устарел: `purchase_order_changed`, `rules_changed`, `duplicates_changed`; воспроизводится |
| D отклонён, A переведён на заказ v2, проверен и сверен заново | `matched`, актуален |
| Правила только для EUR | `no_rule_for_currency` |

`show` выводит снимок со статусом, итогами, расхождениями, цитатами,
актуальностью и признаком `reproducible`.

## 10. Как проверять этап

Команды прежние (см. [инструкцию по тестам](instructions/testing.md)). Тесты
без базы проверяют включительные границы допусков, накопление разниц,
округление HALF_UP на строку, количество и частичное выставление, неизвестные
строки, заголовок и валюту, отсутствие правил, заказа и документа, дубликаты,
детерминизм, проверку правил и хеши. Тесты PostgreSQL проверяют сохранение
входов, повторное использование снимка, цитаты, устаревание после смены
заказа и правил, воспроизведение, новую сверку после `revise`, дубликаты и
отклонение, счёт без документа и заказа, правку правил в обход приложения,
одновременные сверки и демонстрацию в отдельных процессах.

## 11. Ограничения

- `approve` этапа 03 пока не требует снимка сверки: проверка свежего
  `matched`-снимка в транзакции согласования — этап 06.
- Допуски только абсолютные (в деньгах); процентных допусков нет.
- Округление — только 2 знака и `ROUND_HALF_UP`, как в денежном модуле.
- Дубликат — только тот же поставщик и номер счёта.
- Нет налогов, скидок, частичных поставок и учёта ранее оплаченных количеств
  по другим счетам того же заказа.

## 12. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| `no_rule_for_currency` | Добавь правило валюты в новую версию правил |
| `missing_source_document` | Счёт создан кодом; прими документ или отключи требование в правилах |
| Снимок устарел после новой версии заказа | Сделай `revise` на новый заказ, затем `check` и `reconcile` |
| Повторная сверка вернула тот же снимок | Входы не изменились — новый расчёт не нужен |
| `duplicate_invoice` | Отклони лишний процесс или проверь номер счёта |
| `unsupported_rounding` | Поддерживаются только 2 знака и `ROUND_HALF_UP` |
