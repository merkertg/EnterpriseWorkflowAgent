## 1. Что делает этот этап

До этапа 06 решение принимал любой, кто мог вызвать функцию: строка
`actor_id` была просто подписью, а одобрение не смотрело на сверку. Теперь
решение принимает **сотрудник**, которого сервер узнал по токену, у которого
есть нужная **роль** в нужном **подразделении** и который ссылается на
конкретный **свежий снимок сверки без расхождений**.

| Вопрос | Ответ этапа 06 |
| --- | --- |
| Кто вызывает команду? | Сотрудник, найденный по bearer-токену; в базе хранится только SHA-256 токена |
| Что ему можно? | Права ролей `viewer`, `clerk`, `approver` в его подразделениях |
| Можно ли одобрить свой же процесс? | Нет: кто запустил процесс, тот его не одобряет («четыре глаза») |
| Что, если заказ или правила изменились после сверки? | Одобрение отклоняется с `stale_reconciliation`; нужна новая сверка и новое решение |
| Что видит сотрудник другого подразделения? | «Не найдено», как будто процесса нет |
| Как следующий шаг узнает о решении? | Запись outbox в той же транзакции, что и решение |
| Где всё это доступно? | Через HTTP API с токеном и через сервисы Python |

| Уже реализовано | Когда появится остальное |
| --- | --- |
| Сотрудники, роли, подразделения, токены, отзыв и отключение | Агент с инструментами — этап 07 ([реализовано](STAGE_07.md)) |
| HTTP API: загрузка, процесс, сверка, решения, аудит, outbox | Интерфейс Streamlit — этап 08 |
| Одобрение по свежему `matched`-снимку, «четыре глаза» | Доставка событий outbox — этап 09 |
| Outbox и аудит в одной транзакции с решением | Ротация токенов, SSO, ограничение частоты запросов — вне учебного объёма |

Одобрение по-прежнему только завершает учебное согласование: платежей и
обращений к внешним системам нет.

## 2. Сотрудники, роли и подразделения

Сотрудник — запись в таблице `users`: идентификатор, имя, роли, подразделения
и флаг `active`. Роль описывает должность, а права — конкретные действия:

| Роль | `view` | `submit` | `reconcile` | `decide` |
| --- | --- | --- | --- | --- |
| `viewer` (наблюдатель) | да | — | — | — |
| `clerk` (специалист) | да | да | да | — |
| `approver` (согласующий) | да | — | да | да |

Этап 07 добавил право `assist` — запуск агента-помощника; его получили
`clerk` и `approver` ([STAGE_07.md](STAGE_07.md)).

`submit` — загрузить документ, запустить, проверить и пересмотреть процесс.
`reconcile` — запустить сверку. `decide` — одобрить или отклонить. Ролей у
человека может быть несколько: у руководителя группы `clerk` и `approver`.

**Подразделение** (`business_unit`) — часть компании, которой принадлежит
процесс, например `DEMO-UNIT-A`. Процесс получает подразделение при запуске,
и специалист может запускать процессы только в своих подразделениях. Всё
остальное проверяется так:

1. Процесс в чужом подразделении — ответ «не найдено» (`not_found`, HTTP 404).
   Сотрудник не узнаёт даже о существовании чужого процесса.
2. Процесс в своём подразделении, но роли не хватает — `missing_permission`
   (HTTP 403).

Справочники — заказы, политики, правила сверки — общие для всех
подразделений; их чтение требует только права `view`.

Учётные записи создаёт администратор из командной строки, через HTTP их не
создать:

```bash
uv run --locked python -m app.users_cli create demo-clerk --name "Fictional clerk" --role clerk --unit DEMO-UNIT-A
uv run --locked python -m app.users_cli token demo-clerk --label laptop
uv run --locked python -m app.users_cli list
uv run --locked python -m app.users_cli deactivate demo-clerk
uv run --locked python -m app.users_cli revoke TOKEN_ID
```

Процессы, созданные до миграции `0004`, получили подразделение `unassigned`.
Их видит только тот, кому администратор дал это подразделение.

## 3. Токены

Токен выглядит как `ewa_` и 43 случайных символа (256 бит из `secrets`).
Команда `token` показывает его **один раз**. В базе хранится только SHA-256:
копия базы не даёт рабочих токенов. Запрос несёт токен в заголовке:

```text
Authorization: Bearer ewa_...
```

Сервер ищет хеш, проверяет, что токен не отозван, а сотрудник активен, и
получает текущие роли и подразделения. Любая неудача — неверный формат,
неизвестный, отозванный токен или отключённый сотрудник — даёт один и тот же
ответ `unauthenticated` (HTTP 401), чтобы по ответу нельзя было подобрать
причину.

Почему не JWT: подписанный токен действует до истечения срока, и отзыв
требует отдельного списка. Здесь каждый запрос всё равно читает базу, поэтому
отзыв и отключение действуют сразу. Для учебного проекта это проще и
надёжнее.

## 4. Где проверяются права

Проверки живут в прикладном слое (`app/application`), а не в маршрутах
HTTP. Маршрут лишь передаёт сервису `Principal` — кто вызывает и с какими
правами. Сервис **внутри транзакции команды** заново читает строку
сотрудника с блокировкой `FOR SHARE` и проверяет:

- сотрудник существует и активен;
- подразделение процесса входит в его подразделения;
- у ролей есть нужное право.

Повторное чтение важно: если администратор отключил сотрудника между входом и
командой, команда отклоняется. Блокировка `FOR SHARE` заставляет одновременное
отключение подождать, пока команда закончится.

Внутренние инструменты (демонстрации этапов 03–05, загрузка справочников)
вызывают сервисы без `actor`. Решения (`approve`, `reject`) без сотрудника
не выполняются никогда.

## 5. Одобрение: что проверяется и в каком порядке

Запрос одобрения содержит ожидаемую версию процесса, ID снимка сверки и
причину. В одной транзакции сервис:

1. Проверяет ключ идемпотентности: повтор того же запроса возвращает прежний
   результат.
2. Сравнивает версию процесса с ожидаемой (`version_conflict`).
3. Перечитывает сотрудника и проверяет подразделение и право `decide`.
4. Проверяет «четыре глаза»: запустивший процесс не одобряет его
   (`self_approval_forbidden`, HTTP 403).
5. Находит снимок и проверяет, что он относится к этому процессу
   (`reconciliation_not_for_workflow`).
6. Берёт блокировки на заказ, правила и номер счёта (раздел 6).
7. Сравнивает входы снимка с текущими: версии счёта и заказа процесса,
   последнюю версию заказа и правил, список дубликатов. Любое отличие —
   `stale_reconciliation` с причинами, например `["rules_changed"]`.
8. Требует статус `matched` (`reconciliation_not_matched`).
9. Даёт домену выполнить переход: он ещё раз проверяет состояние
   `awaiting_approval` и актуальность базовой проверки.
10. Записывает ключ, новую версию процесса со ссылкой на снимок, событие
    outbox и аудит — всё или ничего.

Отклонение проще: роль, подразделение, состояние и outbox. Снимок сверки для
него не нужен — отказать можно и по неполным данным.

## 6. Почему нужны блокировки

Без блокировок возможна гонка:

```text
Одобрение: снимок свежий? да ──────────────── запись решения ── COMMIT
Закупки:            новая версия заказа ── COMMIT
```

Проверка свежести прошла раньше, чем закупки записали новый заказ, и решение
легло на устаревшие данные. Поэтому одобрение берёт транзакционные
advisory-блокировки PostgreSQL на три ключа, а все, кто меняет эти данные,
берут те же ключи:

| Ключ | Кто ещё его берёт |
| --- | --- |
| `purchase-order:<номер заказа>` | Запись новой версии заказа |
| `reconciliation-rules:<ID правил>` | Запись новой версии правил |
| `invoice-number:<поставщик>\|<номер счёта>` | Запуск процесса по тому же счёту (дубликат) |

Блокировка держится до конца транзакции. Кто пришёл вторым, ждёт; после
ожидания он видит уже записанное. Ключи берутся в отсортированном порядке,
поэтому два одобрения не заблокируют друг друга навсегда. Время ожидания
ограничено настройкой сессии `lock_timeout = 5 s`.

## 7. Outbox

Outbox — таблица событий «что произошло», которую потом прочитает
отдельный обработчик. Событие пишется в той же транзакции, что и решение:
нет решения без события и события без решения. Отправлять сообщение прямо из
команды нельзя — при сбое после отправки решение откатится, а сообщение уже
уйдёт.

| Событие | Когда |
| --- | --- |
| `invoice.approved` | Одобрение; в данных есть ID снимка сверки и хеш его входов |
| `invoice.rejected` | Отклонение |

В данных события — только идентификаторы, версии, хеши, подразделение и автор
решения, без текста документа. Таблица `outbox_events` только для
добавления. Запись аудита решения ссылается и на снимок сверки, и на событие
outbox. Доставки событий нет: обработчик с повторами появится на этапе 09.

## 8. HTTP API

```bash
uv run --locked uvicorn app.main:app --host 127.0.0.1 --port 8003
```

Без `DATABASE_URL` работает только `/health`, остальные адреса отвечают
`503 database_not_configured`.

| Метод и адрес | Право | Что делает |
| --- | --- | --- |
| `GET /me` | любой вход | Кто я, роли, подразделения, права |
| `POST /documents?name=...` | `submit` | Загрузка байтов документа (этап 04) |
| `GET /reference/{kind}/{id}` | `view` | Последняя версия заказа, политики или правил |
| `POST /workflows` | `submit` | Запуск процесса в своём подразделении |
| `GET /workflows/{id}` | `view` | Состояние, версия, входы, решение |
| `POST /workflows/{id}/check` | `submit` | Базовая проверка |
| `POST /workflows/{id}/revise` | `submit` | Другие версии входов |
| `POST /workflows/{id}/reconciliations` | `reconcile` | Сверка с правилами |
| `GET /workflows/{id}/reconciliations/latest` | `view` | Последняя сверка и её актуальность |
| `GET /reconciliations/{snapshot_id}` | `view` | Отчёт по снимку |
| `POST /workflows/{id}/approve` | `decide` | Одобрение по снимку |
| `POST /workflows/{id}/reject` | `decide` | Отклонение |
| `GET /workflows/{id}/audit` | `view` | Аудит |
| `GET /workflows/{id}/outbox` | `view` | События решений |

Команды (`POST` процесса, кроме сверки) требуют заголовок `Idempotency-Key`:
1–60 символов из букв, цифр и `. _ : -`. Сервер добавляет к нему ID
сотрудника, поэтому ключи разных людей не пересекаются. Повтор с тем же
ключом и телом возвращает прежний ответ с `"replayed": true`.

Ошибки имеют одну форму `{"error": {"code": ..., "message": ...}}`:

| HTTP | Коды |
| --- | --- |
| 401 | `unauthenticated` |
| 403 | `missing_permission`, `self_approval_forbidden` |
| 404 | `not_found` (в том числе чужое подразделение) |
| 409 | `version_conflict`, `invalid_transition`, `stale_reconciliation` (с `reasons`), `reconciliation_not_matched`, `idempotency_key_reused`, `workflow_exists` |
| 413 | `too_large` — тело больше 1 МиБ, чтение прекращается на лимите |
| 422 | `invalid_request` (список мест без присланных значений), коды отказа документа, `reconciliation_not_for_workflow` |
| 503 | `database_not_configured`, `database_unavailable` |

Тела запросов строгие: лишнее поле или `"2"` вместо `2` — это 422.
Подробные примеры `curl` — в [инструкции по API](instructions/usage.md).

## 9. Миграция `0004`

| Изменение | Зачем |
| --- | --- |
| Таблица `users` | Сотрудники; `CHECK` на известные роли и непустые подразделения |
| Таблица `api_tokens` | Хеш токена (уникальный), метка, время создания и отзыва |
| Таблица `outbox_events` | События решений; триггер запрещает `UPDATE` и `DELETE` |
| `workflows.business_unit`, `created_by`, `decision_reconciliation_id` | Подразделение, автор запуска, снимок решения |
| `audit_events.reconciliation_snapshot_id`, `outbox_event_id` | Связь аудита со снимком и событием |

Существующие процессы получают подразделение `unassigned` через временное
значение по умолчанию, которое миграция сразу удаляет: новые процессы обязаны
назвать подразделение явно. Это проверено на данных, созданных кодом этапа 05.

## 10. Демонстрация

```bash
uv run --locked alembic upgrade head
uv run --locked python -m app.decisions_demo
uv run --locked python -m app.decisions_demo show WORKFLOW_ID
```

Демонстрация создаёт четырёх вымышленных сотрудников с токенами, входит по
этим токенам и проходит сценарий:

| Шаг | Результат |
| --- | --- |
| Наблюдатель одобряет | `missing_permission` |
| Согласующий другого подразделения одобряет | `not_found` |
| Руководитель, запустивший процесс, одобряет | `self_approval_forbidden` |
| Правила изменились после сверки | `stale_reconciliation`, `rules_changed` |
| Новая сверка, но устаревшая версия процесса | `version_conflict` |
| Одобрение по свежему `matched`-снимку | `approved`, событие `invoice.approved` |
| Тот же запрос ещё раз | Прежний ответ, `replayed: true`, второго события нет |
| Отклонение после одобрения | `invalid_transition` |
| Одобрение счёта с расхождением цены | `reconciliation_not_matched` |
| Отклонение этого счёта | `rejected`, событие `invoice.rejected` |
| Вход по отозванному токену и отключённым сотрудником | `unauthenticated` |

Токены в вывод не попадают. `show` читает процесс, аудит и outbox в новом
процессе Python.

## 12. Как проверять этап

Команды прежние (см. [инструкцию по тестам](instructions/testing.md)). Тесты
без базы проверяют матрицу ролей, чужое подразделение, проверку `Principal`,
форму и хеш токенов, отказ неверному токену без обращения к базе,
обязательные подразделение и причину, ответ 503 без базы и схему OpenAPI.

Тесты PostgreSQL проверяют:

- одобрение со снимком, событием outbox и аудитом; повтор без второго
  события; отклонение с событием `invoice.rejected`;
- отказ по роли, подразделению и «четырём глазам» без единой записи;
- чтение и сверку чужим подразделением (404) и наблюдателем (403 на сверку);
- новую версию заказа или правил между сверкой и одобрением;
- снимок с расхождениями, снимок другого процесса и неизвестный снимок;
- отключение и отзыв, которые действуют на следующую команду;
- сбой после записи outbox: откатываются решение, событие и ключ;
- ожидание блокировки писателями заказа, правил и дубликата;
- HTTP API: 401 с `WWW-Authenticate`, `/me`, полный сценарий, 409 со
  списком причин, строгие тела, 413 и 422 при загрузке, 403 для чужого
  подразделения при запуске;
- CLI сотрудников и демонстрацию в отдельных процессах.

## 13. Ограничения

- Учётные записи и токены создаются только из командной строки; срока
  действия токена, ротации, SSO и ограничения частоты запросов нет.
- Права заданы в коде; изменить роли пользователя можно только новой
  учётной записью (команды смены ролей нет).
- Справочники общие для всех подразделений; документы при загрузке не
  привязаны к подразделению.
- Отклонять процесс может и тот, кто его запустил: «четыре глаза» относятся
  только к одобрению.
- События outbox никуда не доставляются до этапа 09.
- HTTP-сервер проверен локально через `uvicorn` на `127.0.0.1`; TLS и
  публикация в сеть вне объёма этапа.

## 14. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| `503 database_not_configured` | Задай `DATABASE_URL` и перезапусти сервер |
| `401 unauthenticated` | Токен не передан, отозван, неверен или сотрудник отключён — выпусти новый |
| `404` для существующего процесса | Процесс в чужом подразделении |
| `403 missing_permission` при запуске | Подразделение в запросе не твоё |
| `409 stale_reconciliation` | Запусти новую сверку и одобри по новому снимку; при новом заказе сначала `revise` |
| `409 version_conflict` | Прочитай процесс заново и повтори с текущей версией |
| `422 invalid_request` про `Idempotency-Key` | Добавь заголовок с ключом 1–60 символов |
| Старые процессы не видны | После миграции они в `unassigned` |
