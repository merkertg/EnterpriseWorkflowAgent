# Этап 01. Каркас проекта и путь HTTP-запроса

Это подробная учебная инструкция для первого этапа EnterpriseWorkflowAgent.
Она объясняет цель будущего продукта, текущие файлы, запуск сервера и путь
одного запроса через приложение. Команды выполняются из корня проекта.

Здесь сохранено объяснение основы этапа 01. Добавленные затем сущности, денежные
правила и переходы процесса описаны отдельно в [этапе 02](STAGE_02.md).

Короткие английские инструкции: [запуск](instructions/quickstart.md),
[использование API](instructions/usage.md), [проверки](instructions/testing.md)
и [структура](instructions/project-structure.md). Описание автоматических
проверок — в [CI/CD](CI_CD.md). Фактические результаты запусков записываются
отдельно в [VERIFICATION.md](VERIFICATION.md).

## 1. Зачем нужен этот проект

Учебный продукт будет помогать согласовывать счета поставщиков по заказам
на закупку. В будущем пользователь сможет передать документ, увидеть
извлечённые поля, проверить их по правилам компании, разобраться в расхождениях
и передать счёт на следующий шаг согласования. Заказ на закупку будет
структурированным основанием для сверки счёта.

Для демонстрации будут использоваться вымышленные компании, документы,
суммы и сотрудники. На первом этапе таких данных ещё нет. Приложение пока
не принимает счета, не извлекает поля, не запускает согласование и не обращается
к языковой модели.

Задача этапа 01 — подготовить небольшой работающий фундамент. Сначала нужно
понять, как сервер принимает запрос, как настройки попадают в приложение,
как формируется ответ и как проверить этот путь автоматически. После этого
бизнес-логику можно добавлять небольшими проверяемыми частями.

## 2. Что реализовано на этапе 01

| Часть | Назначение |
| --- | --- |
| FastAPI-приложение | Обрабатывает служебный запрос `GET /health` |
| Pydantic-схема `HealthResponse` | Задаёт структуру ответа: `status` и `service` |
| Настройки `Settings` | Читают имя сервиса, окружение и режим отладки |
| Фабрика `create_app()` | Создаёт приложение с выбранными настройками |
| pytest | Проверяет API и поведение настроек без внешнего сервера |
| Ruff и mypy | Проверяют оформление, частые ошибки и типы |
| `uv.lock` | Фиксирует версии зависимостей |
| GitHub Actions | Описывает автоматическое выполнение проверок |
| Проверка ссылок | Находит отсутствующие локальные цели Markdown-ссылок |

База данных, обработка документов, правила согласования, авторизация,
LLM, интерфейс и развёртывание относятся к следующим этапам. Наличие
файла workflow означает, что CI настроен в репозитории. Успех удалённого
запуска подтверждается отдельно по результату GitHub Actions.

## 4. Первый запуск на Mac

### 4.1. Открыть корень проекта

```bash
cd "/Users/arslanbakiev/Desktop/AI Forge/EnterpriseWorkflowAgent"
```

Кавычки нужны из-за пробела в `AI Forge`. Корень проекта — папка,
в которой лежит `pyproject.toml`. Если запускать команды из другой папки,
Python может не найти пакет `app`, а uv — нужный проект.

### 4.2. Проверить uv и подготовить зависимости

```bash
uv --version
uv sync --locked
uv run --locked python --version
```

uv управляет Python, окружением и зависимостями проекта. Если команда
`uv --version` не найдена, сначала установи uv по его официальной инструкции.
После установки открой новую вкладку терминала.

`uv sync --locked` создаёт `.venv` и устанавливает зависимости из `uv.lock`.
Флаг `--locked` требует согласованности `uv.lock` и `pyproject.toml`.
Если они расходятся, команда завершится ошибкой, а не обновит lock-файл
незаметно. Проект использует Python `>=3.12,<3.13`; ожидается Python 3.12.x.

Для стандартного запуска файл `.env` не обязателен: у всех текущих настроек
есть значения по умолчанию. Если нужны свои значения, открой `.env.example`
и создай рядом `.env`, предварительно убедившись, что такой файл ещё
не существует. Существующий `.env` не нужно перезаписывать.

### 4.3. Запустить сервер

```bash
uv run --locked uvicorn app.main:app --reload --host 127.0.0.1 --port 8003
```

Разбор команды:

| Часть | Значение |
| --- | --- |
| `uv run --locked` | Запустить команду в окружении этого проекта |
| `uvicorn` | Запустить HTTP-сервер для ASGI-приложения |
| `app.main:app` | Из модуля `app/main.py` взять объект с именем `app` |
| `--reload` | Перезапускать сервер при изменении Python-файлов |
| `--host 127.0.0.1` | Слушать локальный адрес компьютера |
| `--port 8003` | Использовать порт 8003 |

Сервер занимает эту вкладку терминала до остановки. Для следующих команд
открой вторую вкладку. Остановить сервер можно сочетанием `Ctrl+C`.
Режим `--reload` предназначен для локальной разработки.

### 4.4. Отправить первый запрос

```bash
curl -i http://127.0.0.1:8003/health
```

При стандартных настройках ожидаются HTTP-код `200` и JSON:

```json
{"status": "ok", "service": "enterprise-workflow-agent"}
```

`curl` — программа для HTTP-запросов из терминала. Флаг `-i` добавляет к телу
ответа строку статуса и заголовки. Пробелы и порядок ключей JSON могут
отличаться: важны сами поля и значения.

Открой также:

- <http://127.0.0.1:8003/docs> — Swagger UI, где можно отправить запрос;
- <http://127.0.0.1:8003/redoc> — другое представление документации API;
- <http://127.0.0.1:8003/openapi.json> — описание API в формате OpenAPI.

В `/docs` раскрой `GET /health`, нажми **Try it out**, затем **Execute**.
Внизу страницы найди `HealthResponse`: FastAPI описывает ответ через эту схему.

## 5. Путь запроса от клиента до JSON

```text
Браузер или curl
    │ GET http://127.0.0.1:8003/health
    ▼
Uvicorn: принимает соединение и передаёт запрос приложению
    ▼
FastAPI: выбирает маршрут по методу GET и пути /health
    ▼
health(): берёт настройки из request.app.state.settings
    ▼
HealthResponse: status="ok", service=settings.app_name
    ▼
FastAPI и Pydantic: проверяют структуру и сериализуют ответ
    ▼
HTTP 200, Content-Type: application/json
```

Клиент — программа, которая отправляет запрос. Сервер — программа, которая
его принимает и отвечает. HTTP — протокол их общения. `GET` — метод чтения,
`/health` — путь ресурса, а `8003` — номер порта, на котором слушает сервер.

Uvicorn и FastAPI выполняют разные задачи. Uvicorn работает с соединением
и передаёт запрос по интерфейсу ASGI. FastAPI выбирает Python-функцию,
вызывает её и готовит HTTP-ответ. ASGI — соглашение о взаимодействии
Python-сервера и асинхронного веб-приложения.

JSON — текстовый формат обмена данными. Python-объект `HealthResponse`
живёт внутри процесса. Чтобы клиент мог прочитать его по сети, приложение
превращает значения полей в JSON. Этот процесс называется сериализацией.

`/health` отвечает только на вопрос «процесс приложения способен обработать
этот HTTP-запрос?». Ответ `ok` не доказывает работу базы данных, LLM,
обработки документов или полного процесса согласования.

## 6. Пакеты, модули и точка входа

Модуль — Python-файл. Например, `app/config.py` импортируется как
`app.config`. Пакет объединяет модули: `app`, `app.api` и `app.api.routes`
образуют вложенную структуру.

Когда Uvicorn читает `app.main:app`, он импортирует `app.main`. При импорте
Python выполняет код верхнего уровня этого модуля. Поэтому строка
`app = create_app()` создаёт объект приложения, который затем получает сервер.

`app/__init__.py` хранит версию приложения. Она должна согласовываться
с версией проекта в `pyproject.toml`. Это помогает понять, какой вариант кода
запущен, и делает описание OpenAPI согласованным с проектом.

Один объект `app` нужен для обычного запуска. Отдельная функция
`create_app()` нужна, чтобы тесты или будущие команды могли создавать
независимые приложения с разными настройками.

## 7. Настройки: Settings и get_settings()

Класс `Settings` в `app/config.py` описывает текущую конфигурацию:

| Поле Python | Переменная окружения | По умолчанию | Что означает |
| --- | --- | --- | --- |
| `app_name` | `APP_NAME` | `enterprise-workflow-agent` | Имя сервиса в API |
| `app_env` | `APP_ENV` | `development` | Метка окружения |
| `app_debug` | `APP_DEBUG` | `false` | Режим локальной отладки |

`app_env` принимает только `development`, `test` или `production`.
Ограничение задаётся типом `Literal`: произвольная строка вроде `prod`
не является допустимым значением.

Имя сервиса очищается от пробелов по краям и должно содержать хотя бы один
символ. `APP_NAME="   "` не подходит. Pydantic проверяет эти ограничения
при создании `Settings`, поэтому ошибка обнаруживается при запуске,
а не после первого пользовательского запроса.

Для обычного `Settings()` приоритет источников такой: переменная окружения
процесса → `.env` в корне проекта → значение по умолчанию. Если создать
объект с явными параметрами, например `Settings(app_name="training")`,
они имеют приоритет над внешними источниками.

В `.env` строки выглядят так:

```dotenv
APP_NAME=enterprise-workflow-agent
APP_ENV=development
APP_DEBUG=false
```

Неизвестные ключи `.env` игнорируются благодаря `extra="ignore"`. Это
не значит, что опечатка исправится сама: `APP_NMAE` будет проигнорирован,
а имя останется значением по умолчанию. Текущий пример не содержит секретов.
Реальные ключи внешних сервисов, когда они понадобятся, должны храниться
в локальных настройках, а не в Git.

`APP_ENV=production` сейчас является меткой окружения. Она не развёртывает
сервис и не добавляет авторизацию. `APP_DEBUG` также не управляет правами
пользователей: режим отладки не является механизмом доступа.

Функция `get_settings()` создаёт `Settings`. Декоратор `lru_cache` сохраняет
результат, чтобы повторные вызовы не перечитывали окружение и `.env`.
После изменения настроек перезапусти сервер. В тестах кэш можно очистить
через `get_settings.cache_clear()`, когда нужно повторно прочитать источники.

## 8. Фабрика приложения create_app()

Функция объявлена в `app/main.py`:

```python
def create_app(settings: Settings | None = None) -> FastAPI: ...
```

Это сигнатура: она показывает имя функции, входной параметр и тип результата.
`Settings | None` означает «объект настроек или отсутствие значения».
`= None` делает параметр необязательным. `-> FastAPI` сообщает, что функция
возвращает приложение FastAPI. Многоточие здесь сокращает тело для объяснения;
рабочая реализация находится в исходном файле.

Если настройки переданы явно, функция использует их. Если нет — вызывает
`get_settings()`. Затем создаёт FastAPI, сохраняет выбранные настройки
в `application.state.settings` и подключает маршруты через `include_router()`.

`state` — место для данных конкретного экземпляра приложения. Благодаря ему
обработчик `/health` читает настройки того приложения, которое получило
запрос. В тестах можно создать два экземпляра с разными именами, и каждый
должен вернуть собственное имя сервиса.

Схема создания выглядит так:

```text
create_app(настройки или None)
    → выбор Settings
    → объект FastAPI
    → application.state.settings
    → include_router(health_router)
    → готовое приложение
```

Это небольшой первый шаг к разделению ответственности. `main.py` собирает
приложение, `config.py` описывает настройки, а файл маршрута отвечает за HTTP.

## 9. Обработчик health() и Request

В `app/api/routes/health.py` находится объект `APIRouter`. Роутер собирает
связанные маршруты, чтобы `main.py` не превращался в большой список функций.
В будущем для документов и согласований появятся отдельные роутеры.

Декоратор маршрута связывает метод `GET` и путь `/health` с функцией `health()`.
Параметр `response_model=HealthResponse` указывает FastAPI, какую структуру
нужно вернуть и показать в OpenAPI.

FastAPI передаёт в функцию `Request` — объект текущего HTTP-запроса.
Через `request.app` обработчик получает приложение, а через
`request.app.state.settings` — его настройки. В ответ попадают `status="ok"`
и имя из `app_name`.

`cast(Settings, ...)` уточняет тип для mypy: «здесь ожидается `Settings`».
Он не создаёт настройки и не проверяет объект во время выполнения.
Корректный объект заранее сохраняет функция `create_app()`.

На этом этапе обработчик не читает тело запроса, файл, токен или базу.
Поэтому `curl` не нужны дополнительные параметры и заголовки авторизации.
Обычный `POST /health` должен получить `405 Method Not Allowed`: путь есть,
но такой HTTP-метод для него не зарегистрирован.

## 10. Схема ответа HealthResponse

`app/api/schemas/health.py` определяет модель Pydantic. Её поля:

- `status` ограничен значением `"ok"`;
- `service` содержит строку с именем сервиса.

`Literal["ok"]` точнее, чем просто `str`: статусом не может стать
произвольное слово. Pydantic проверяет данные модели, а FastAPI использует
её как договор между сервером и клиентом.

Схема данных и бизнес-правило — разные понятия. `HealthResponse` описывает
служебный ответ API. Она ещё не проверяет сумму счёта, поставщика, наличие
заказа на закупку или полномочия согласующего. Такие правила появятся вместе
с предметной областью на следующих этапах.

## 11. Автоматические тесты

Запусти:

```bash
uv run --locked pytest
```

pytest находит тестовые функции в `tests/`, выполняет их и сообщает,
какие проверки прошли. `assert` внутри теста сравнивает фактический результат
с ожидаемым. Если сравнение неверно, тест падает и показывает расхождение.

`TestClient` из FastAPI позволяет отправлять запросы приложению прямо из
теста. Для него не нужно отдельно запускать Uvicorn или освобождать порт 8003.
Это проверяет маршрутизацию и ответы приложения, но само по себе не доказывает
работу настоящего сетевого сервера. Локальный запрос через `curl` проверяет
этот дополнительный участок.

В текущем lock-файле для TestClient установлен пакет `httpx2`: его использует
выбранная версия Starlette, на которой основан FastAPI. Поэтому в dev-зависимостях
указан `httpx2`, а не `httpx` из более старых примеров. Нужную совместимую
версию устанавливает `uv sync --locked`.

Проверки этапа относятся к нескольким группам:

| Группа | Что нужно подтвердить |
| --- | --- |
| API | `GET /health`, структура JSON, имя сервиса, неверный HTTP-метод |
| Документация API | Доступность `/docs`, `/redoc`, описание OpenAPI |
| Настройки | Значения по умолчанию, источники, допустимые значения |
| Фабрика | Разные приложения используют собственные настройки |
| Версия API | Версия в OpenAPI совпадает с `app.__version__` |

В `tests/conftest.py` находятся фикстуры — подготовка окружения для тестов.
Фикстура `isolated_settings` переводит тест во временную папку `tmp_path`,
убирает `APP_*` из его окружения и очищает кэш настроек. Благодаря этому
тестовый `.env` создаётся во временной папке, а личный `.env` разработчика
не читается и не перезаписывается.

`monkeypatch` временно меняет окружение или текущую папку и восстанавливает
их после теста. `yield` в фикстуре разделяет подготовку и завершение:
до него выполняется настройка, после него — очистка. Фикстура `client`
создаёт тестовое приложение внутри `with TestClient(...)`, чтобы клиент
корректно завершил работу после проверки.

Число тестов и результаты последнего фактического запуска смотри
в [отчёте проверки](VERIFICATION.md). Текст инструкции не является
свидетельством того, что команда была выполнена.

## 12. Проверки качества и воспроизводимость

Запускай из корня проекта:

```bash
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked pytest
uv run --locked python scripts/check_docs.py
```

| Команда | Что она проверяет |
| --- | --- |
| `ruff check .` | Типичные ошибки Python и правила оформления |
| `ruff format --check .` | Соответствие форматированию без изменения файлов |
| `mypy app tests scripts` | Совместимость типов в строгом режиме |
| `pytest` | Поведение программы на заданных сценариях |
| `check_docs.py` | Существование локальных целей Markdown-ссылок |

mypy читает аннотации вроде `Settings | None` и `-> FastAPI`. Он может найти
несовместимые типы до запуска, но не заменяет тесты. Ruff также не доказывает
правильность бизнес-логики: хорошо оформленная программа всё ещё может
содержать логическую ошибку.

`pyproject.toml` описывает зависимости и настройки инструментов. `uv.lock`
фиксирует результат разрешения зависимостей, включая транзитивные пакеты —
библиотеки, которые нужны другим библиотекам. `.python-version` выбирает
ветку Python 3.12. `.venv` хранит установленное окружение и не включается
в Git: его восстанавливают из файлов проекта.

GitHub Actions повторяет проверки в отдельной среде после событий,
указанных в workflow. Локальный успешный запуск и удалённый успешный запуск
фиксируются отдельно. Подробности — в [CI_CD.md](CI_CD.md).

## 13. Типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| `uv: command not found` | Установлен ли uv и открыта ли новая вкладка терминала после установки |
| `pyproject.toml` не найден | Выполняется ли команда из корня EnterpriseWorkflowAgent |
| `No module named app` | Текущую папку и запуск через `uv run --locked` |
| Python другой версии | `uv run --locked python --version`; системный `python3` может отличаться |
| `Address already in use` | Не работает ли другой сервер на 8003; остановить его или выбрать свободный порт |
| `curl: Failed to connect` | Запущен ли Uvicorn и совпадает ли порт с URL |
| `/health` вернул `404` | Нет ли опечатки в пути; нужен именно `/health` |
| `/health` вернул `405` | Используется ли `GET`, а не `POST` |
| Ошибка валидации `Settings` | Не пуст ли `APP_NAME`; входит ли `APP_ENV` в допустимый список |
| Изменения `.env` не видны | Перезапустить сервер; настройки кэшируются |
| Имя не изменилось | Нет ли опечатки `APP_NAME` или более приоритетной переменной окружения |
| `uv sync --locked` отклоняет lock | Не менялся ли `pyproject.toml` без согласованного обновления `uv.lock` |
| Проверки зелёные локально, а CI не виден | Проверить отдельный запуск GitHub Actions для нужного коммита |

Если выбран другой порт, например `--port 8013`, этот же номер нужно
использовать во всех URL для браузера и `curl`.

## 14. Как разбирать код самостоятельно

1. Запусти сервер и отправь `GET /health` через `/docs` и `curl`.
2. Открой `app/main.py`: найди `app = create_app()` и подключение роутера.
3. Открой `app/config.py`: сопоставь каждое поле с переменной окружения.
4. Открой `app/api/routes/health.py`: найди получение настроек из запроса.
5. Открой `app/api/schemas/health.py`: сопоставь поля с JSON-ответом.
6. Прочитай тест API и найди, где сравниваются код и тело ответа.
7. Запусти весь набор проверок из раздела 12.

После объяснения попробуй ответить своими словами:

- Зачем одновременно нужны Uvicorn и FastAPI?
- Что означает каждая часть `app.main:app`?
- Почему настройки хранятся в объекте конкретного приложения?
- Чем `Settings` отличается от `HealthResponse`?
- Почему `APP_NAME="   "` должен вызвать ошибку?
- Что проверяет `/health`, а какие части будущего продукта он не проверяет?
- Почему успешные тесты с `TestClient` полезно дополнить запросом к Uvicorn?
- Чем конфигурация CI отличается от подтверждённого запуска на GitHub?

На следующем этапе полезно переходить к предметной области: назвать
сущности заказа на закупку, счёта, расхождения и решения согласующего, определить
допустимые состояния и проверить переходы обычным Python-кодом.
Полный агентский цикл добавляется после понятных и проверяемых правил.
