## 1. Что делает этот этап

С этапа 06 решение сотрудника записывает событие `invoice.approved` или
`invoice.rejected` в outbox, но никуда его не отправляет. Этап 09 добавляет
**обработчик outbox**: он доставляет события единственному получателю —
вымышленной «следующей системе» на `127.0.0.1` — с подписью, ограниченными
повторами и видимым состоянием доставки.

Второй результат — **набор оценок**: 31 именованный сценарий с заранее
записанным ожидаемым итогом. Сценарии проверяют вредоносные инструкции в
документе, ошибочные и неоднозначные поля, отказ и медленный ответ модели,
повторы, конкуренцию, вредоносные файлы и права доступа.

Третий — **усиление ограничений**: процесс чтения PDF ограничивает своё
процессорное время, память (там, где ОС это позволяет) и объём текста; тело
команды API не больше 64 КиБ; помощника нельзя запускать для одного процесса
чаще 20 раз в час.

| Вопрос | Ответ этапа 09 |
| --- | --- |
| Куда уходит событие? | Только на `SANDBOX_WEBHOOK_URL` — адрес обязан быть `127.0.0.1` или `[::1]` |
| Может ли документ или запрос выбрать адрес? | Нет: адрес задаёт только настройка, перенаправления и прокси отключены |
| Что, если получатель недоступен? | Повтор через 2, 4, 8, 16 с; после 5 попыток — `exhausted` |
| Теряется ли событие при сбое обработчика? | Нет: попытка фиксируется вместе с состоянием, иначе событие остаётся в очереди |
| Создаёт ли повтор второе действие у получателя? | Нет: получатель учитывает ID события и отвечает `duplicate` |
| Видит ли сотрудник, что доставка не удалась? | Да: API и страница показывают статус, попытки и ошибку |
| Подтверждают ли оценки готовность к эксплуатации? | Нет: это небольшой вымышленный набор с детерминированными провайдерами |

| Уже реализовано | Когда появится остальное |
| --- | --- |
| Обработчик outbox, подписанный sandbox webhook, журнал попыток | Настоящий внешний получатель — вне объёма проекта |
| Повторная постановка исчерпанного события оператором | Docker и compose — этап 10 |
| 31 сценарий оценки с отчётом и ограничениями | Оценка настоящей LLM — не выполнялась |
| Лимиты PDF-процесса, размера тела команды, квота помощника | Ограничение памяти на macOS — ОС не позволяет |

## 2. Как запустить

```bash
uv run --locked alembic upgrade head
export SANDBOX_WEBHOOK_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
uv run --locked python -m sandbox.receiver
uv run --locked python -m app.outbox_worker run
```

Получатель и обработчик запускаются в разных терминалах с одним и тем же
`SANDBOX_WEBHOOK_SECRET` (не короче 32 символов). Обработчику нужен ещё
`DATABASE_URL`. Секрет не хранится в репозитории; в `.env.example` есть
только пустая строка-подсказка.

| Команда | Что делает |
| --- | --- |
| `python -m sandbox.receiver` | Получатель на `127.0.0.1:8010`, данные в `var/sandbox/receiver.sqlite3` |
| `python -m sandbox.receiver --mode fail` | Отвечает 503 на всё — чтобы увидеть повторы и исчерпание |
| `python -m app.outbox_worker run` | Доставляет события каждые 2 с; Ctrl+C останавливает |
| `python -m app.outbox_worker run --once` | Доставляет то, что пора, и завершается |
| `python -m app.outbox_worker status` | Число событий по статусам и список исчерпанных |
| `python -m app.outbox_worker requeue EVENT_ID` | Новый круг попыток для исчерпанного события |
| `python -m app.outbox_demo` | Демонстрация всех видов сбоя без второго терминала |
| `python -m app.evals run` | Все сценарии оценки; отчёты в `var/evals/` |
| `python -m app.evals list` | Сценарии и их ожидаемые итоги, без базы |

Коды завершения обработчика: 0 — успешно, 1 — ошибка базы или команды,
2 — нет `DATABASE_URL`, секрета или адрес не loopback.

## 3. Состояние доставки

Таблица `outbox_events` с этапа 06 только дополняется. Изменяемое состояние
доставки лежит рядом, в `outbox_deliveries` (одна строка на событие), а
каждая попытка — в журнале `outbox_attempts`, который тоже только
дополняется.

| Статус | Значение |
| --- | --- |
| `pending` | Попыток в этом круге ещё не было |
| `retry_scheduled` | Попытка не удалась; следующая — в `next_attempt_at` |
| `delivered` | Получатель ответил 2xx |
| `exhausted` | Пять попыток подряд не удались; нужен оператор |

Строка доставки создаётся **в той же транзакции**, что решение, событие и
аудит. Поэтому не бывает события без состояния, которое обработчик мог бы
пропустить. Миграция `0006` создала строки `pending` и для событий,
записанных до неё.

В журнале попытки хранятся номер, время, длительность, итог, код HTTP или
код ошибки (`http_503`, `timeout`, `connection_error`, `redirect_refused`) и
признак `duplicate` из ответа получателя. Тела запроса и секрета в журнале
нет.

## 4. Как обработчик берёт событие

```text
транзакция:
  SELECT … FROM outbox_deliveries
   WHERE status IN ('pending', 'retry_scheduled') AND next_attempt_at <= now
   ORDER BY next_attempt_at LIMIT 1
   FOR UPDATE SKIP LOCKED          ← другой обработчик эту строку пропустит
  подписать и отправить (таймаут 5 с)
  INSERT outbox_attempts; UPDATE outbox_deliveries
COMMIT
```

Блокировка строки держится, пока идёт отправка. Если запустить два
обработчика, каждый возьмёт разные события. Если обработчик упал после
отправки, но до `COMMIT`, транзакция откатится и событие снова станет
доступным. Получатель к тому моменту уже мог выполнить действие — поэтому
он сам отбрасывает повтор по ID события.

Это доставка **как минимум один раз**. Ровно-один-раз по сети не
обещается: обещание «один раз» выполняет получатель, а не сеть.

Задержки повторов растут вдвое: 2, 4, 8, 16 с (не больше 60). Случайного
разброса нет, чтобы тесты и демонстрация были воспроизводимы. После пятой
неудачи статус `exhausted`: событие больше не берётся. Оператор исправляет
получателя и выполняет `requeue` — счётчик круга обнуляется, номера попыток
продолжаются, журнал сохраняется.

## 5. Подпись и получатель

Тело — канонический JSON (ключи по алфавиту, без пробелов): ID события, тип,
процесс, версия, время создания и `payload` (только ID и хеши). Заголовки:

| Заголовок | Содержимое |
| --- | --- |
| `X-EWA-Event-Id` | ID события; совпадает с полем в теле |
| `X-EWA-Timestamp` | Время подписи, секунды Unix |
| `X-EWA-Signature` | `v1=` и HMAC-SHA256 от `timestamp.тело` |

Получатель (`sandbox/receiver.py`) **не импортирует `app`** и проверяет
подпись своим кодом, как настоящая внешняя система. Тест архитектуры
следит за этой границей. Порядок проверок:

1. Тело не больше 64 КиБ — иначе `413 too_large`.
2. Заголовки разбираются — иначе `400 invalid_headers`.
3. Время подписи в пределах ±300 с — иначе `401 stale_timestamp` (защита от
   повторной отправки перехваченного запроса).
4. Подпись совпадает (`hmac.compare_digest`) — иначе `401 bad_signature`.
5. ID в теле равен заголовку — иначе `400 invalid_body`.
6. Действие: первая доставка записывает строку в SQLite (`accepted`), повтор
   только увеличивает счётчик (`duplicate`), тот же ID с другим телом —
   `409 event_id_reused`.

«Бизнес-действие» получателя — одна строка о том, что решение пришло.
Платежей, писем и проводок нет.

Режимы для учебных сбоев: `fail` — 503 до действия; `lose_ack` — действие
выполнено, но ответ «потерян» (503); `slow` — ответ после задержки. Флаг
`--failures N` применяет режим к N запросам, потом получатель снова
принимает.

## 6. Почему адрес нельзя подменить

- URL задаётся только настройкой `SANDBOX_WEBHOOK_URL`; при старте он
  проверяется: схема `http`/`https`, хост — IP-адрес `127.0.0.1` или `::1`,
  без логина, пароля и параметров. Имя `localhost` не принимается: его
  можно направить в другое место через `/etc/hosts`.
- Ни событие, ни документ, ни HTTP-запрос не содержат адреса доставки.
- HTTP-клиент на `urllib` отключает прокси из переменных окружения и не
  следует перенаправлениям (`redirect_refused`), поэтому ответ получателя
  тоже не может увести событие.

## 7. Видимость для сотрудника

`GET /workflows/{id}/outbox` теперь возвращает у каждого события блок
`delivery` (статус, попытки, следующая попытка, последняя ошибка, время
доставки) и список `attempts`. Права прежние: `view` в своём
подразделении.

Страница Streamlit показывает статус в таблице событий. Для
`retry_scheduled` — жёлтое предупреждение с ошибкой и временем следующей
попытки. Для `exhausted` — красное сообщение с числом попыток, ошибкой и
командой `requeue` для оператора. Кнопки повторной постановки на странице
нет: это действие оператора, а не согласующего.

## 8. Усиленные ограничения

| Ограничение | Как работает | Код отказа |
| --- | --- | --- |
| Процессорное время PDF-процесса | `RLIMIT_CPU` = таймаут, округлённый вверх | `resource_limit` |
| Память PDF-процесса | `RLIMIT_AS` 512 МиБ; Linux применяет, macOS отказывает — процесс сообщает, что лимита нет | `resource_limit` |
| Текст PDF | Считается внутри процесса по мере чтения страниц | `text_too_long` |
| Процесс убит сигналом | Отрицательный код завершения | `resource_limit` |
| Тело команды API | `Content-Length` не больше 64 КиБ, иначе 413; тело без длины — 411 | `too_large`, `length_required` |
| Помощник | Не больше 20 запусков на процесс за скользящий час | `429 agent_run_limit` |

Загрузка документа (`POST /documents`) по-прежнему читает тело потоком с
лимитом 1 МиБ и в проверку 64 КиБ не входит.

Квота помощника считает строки `agent_runs` без блокировки: два
одновременных запроса на границе могут пройти оба. Это ограничение
стоимости, а не замок.

## 9. Оценки

Каждый сценарий — функция, которая запускает настоящие сервисы на
PostgreSQL (а для доставки — настоящий получатель на loopback) и
возвращает наблюдение. Ожидаемое наблюдение записано рядом заранее;
сценарий пройден, только если они равны целиком.

| Категория | Сценариев | Пример |
| --- | --- | --- |
| `injection` | 3 | Модель выполняет текст из поля и вызывает `approve_workflow` — отказ `unknown_tool` |
| `wrong_fields` | 3 | Цена на 0,10 ниже заказа: проверка проходит, сверка — нет, одобрение отклонено |
| `ambiguous_data` | 3 | Два разных итога в документе — `ambiguous_field`, счёта нет |
| `provider_failure` | 3 | Провайдер падает при извлечении — `needs_review`, поля пусты |
| `timeout` | 3 | Получатель отвечает после таймаута, но действует; повтор — `duplicate` |
| `retry` | 4 | Получатель недоступен: три попытки, `exhausted`, после `requeue` — `delivered` |
| `concurrency` | 2 | Два одобрения одновременно: одно проходит, одно событие |
| `malicious_document` | 6 | PDF с паролем, PNG вместо текста, текст длиннее лимита |
| `access` | 4 | Третий запуск помощника при квоте 2 — `agent_run_limit` |

```bash
uv run --locked python -m app.evals run
uv run --locked python -m app.evals run --case retry-webhook-lost-answer
```

Отчёт пишется в `var/evals/eval-<время>-<запуск>.json` и `.md`. В нём итог по
категориям, ожидание и наблюдение каждого сценария и раздел ограничений:
провайдеры детерминированные, набор маленький и написан авторами кода, всё
на одной машине, лимит памяти только на Linux, прохождение набора — не
заявление о готовности к эксплуатации. Тест
`tests/persistence/test_evals.py` запускает весь набор на тестовой базе.

Перед сценариями доставки контекст доставляет все ожидающие события своему
временному получателю. Поэтому на общей базе разработки события прежних
запусков будут отмечены как доставленные в этот получатель; их число
указано в отчёте (`earlier_events_sent_to_eval_receiver`). То же делает
`app.outbox_demo`.

При первом прогоне три ожидания были записаны неверно, код был прав:
у сверки нет статуса `not_matched` (есть `matched` и `needs_review`), а итог
31.00 при заказе на 30.00 даёт два кода, как описано на этапе 02. Ожидания
исправлены по документированным правилам, а не подогнаны под случайный
результат.

## 12. Ограничения

- Получатель — учебная заглушка на SQLite в том же компьютере; сетевых
  сбоев, кроме отказа соединения, кодов ошибок и медленных ответов, нет.
- Доставка как минимум один раз; дедупликация — обязанность получателя.
- Блокировка строки держится во время отправки (до 5 с). Для учебного
  объёма это проще аренды; при большой нагрузке стоило бы сначала записать
  аренду, а отправлять вне транзакции.
- Повторной постановки со страницы нет; `requeue` — команда оператора без
  записи в аудит процесса (видна по счётчику `requeues`).
- Лимит памяти PDF-процесса на macOS не действует; на Linux не проверен
  локально.
- Квота помощника может быть превышена на один запуск при одновременных
  запросах.
- Оценки используют только детерминированные провайдеры; поведение
  настоящей LLM не измерялось.

## 13. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| `Set SANDBOX_WEBHOOK_SECRET` | Задай секрет 32+ символов и обработчику, и получателю |
| `Invalid settings: sandbox_webhook_url` | Адрес не `127.0.0.1`/`[::1]` или с параметрами |
| Все попытки `http_401` | Разные секреты у обработчика и получателя или часы расходятся больше чем на 5 минут |
| Все попытки `connection_error` | Получатель не запущен или другой порт |
| Событие `exhausted` | Исправь получателя и выполни `outbox_worker requeue EVENT_ID` |
| `429 agent_run_limit` | Час ещё не прошёл с 20 запусков помощника для этого процесса |
| `411 length_required` | Клиент отправил тело без `Content-Length` |

## 14. Вопросы после разбора

1. Почему строка доставки создаётся в транзакции решения, а не обработчиком?
2. Что произойдёт, если обработчик упадёт между отправкой и `COMMIT`?
3. Почему повтор не создаёт второго действия, хотя сеть может доставить дважды?
4. Зачем `SKIP LOCKED`, если можно просто `FOR UPDATE`?
5. Почему в подписи есть время, и что даёт окно ±300 с?
6. Почему имя `localhost` не принимается, а `127.0.0.1` — да?
7. Почему таймаут не означает, что получатель ничего не сделал?
8. Чем ожидание сценария оценки отличается от «того, что получилось»?
9. Почему успех всех оценок не значит готовность к эксплуатации?

Следующий этап — воспроизводимый выпуск: Docker, compose, расширенный CI и
восстановление учебных данных.
