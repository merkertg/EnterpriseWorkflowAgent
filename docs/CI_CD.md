# CI/CD: автоматические проверки проекта

На этапе 01 подготовлена конфигурация CI в `.github/workflows/ci.yml`.
Она описывает проверки кода и документации. Автоматическое развёртывание
и публикация приложения на этом этапе не реализованы.

CI, continuous integration, — автоматические проверки изменений в отдельной
среде. CD, continuous delivery/deployment, — подготовка или доставка приложения
в среду запуска. Эти задачи добавляются отдельно по мере развития проекта.

## Когда запускаются проверки

Текущий workflow реагирует на `push` в `main`, pull request в `main`
и ручной запуск через `workflow_dispatch`. Задание **Lint, types, tests
and documentation** выполняется на `ubuntu-24.04` с Python 3.12
и uv 0.12.23. Удалённый запуск ограничен пятнадцатью минутами. GitHub Actions
получает право чтения содержимого репозитория; публикация или развёртывание
в этом задании не предусмотрены.

## Что проверяет workflow

| Проверка | Команда | Для чего |
| --- | --- | --- |
| Зависимости | `uv sync --locked --group ui` | Установить согласованный набор из lock-файла вместе с группой интерфейса |
| Lint | `uv run --locked ruff check .` | Найти типичные ошибки и нарушения правил |
| Форматирование | `uv run --locked ruff format --check .` | Проверить оформление без правок |
| Типы | `uv run --locked --group ui mypy app tests scripts migrations ui sandbox` | Проверить типы в строгом режиме |
| Миграции | `uv run --locked alembic upgrade head` | Применить схему к тестовой базе CI |
| Схема и модели | `uv run --locked alembic check` | Убедиться, что модели не разошлись с миграциями |
| Тесты | `uv run --locked --group ui pytest` | Проверить поведение, включая тесты PostgreSQL и оценки |
| Ссылки | `uv run --locked python scripts/check_docs.py` | Проверить локальные ссылки Markdown |

Этап 01 не требовал базы данных, Docker, корпоративных учётных записей
или ключа LLM. В текущие проверки не входят извлечение полей документа,
HTTP-согласование счёта или работа настоящей модели: этой реализации ещё нет.

На этапе 02 тот же `pytest` автоматически находит тесты в `tests/domain/` и
проверку CLI. Доменные модели, базовые правила и переходы состояний проверяются
без сервисов; реальные права пользователя и HTTP-команды согласования ещё
не реализованы. Базовые сценарии можно запустить отдельно:
`uv run --locked python -m app.demo`.

## PostgreSQL в CI (этап 03)

Задание запускает сервисный контейнер `postgres:18.3`, закреплённый по
digest-хешу образа, — той же версии, на которой выполнялась локальная проверка.
Контейнер создаёт пустую базу `enterprise_workflow_test`; GitHub Actions
дожидается проверки готовности `pg_isready` перед шагами задания.

Переменные задания:

| Переменная | Значение и смысл |
| --- | --- |
| `TEST_DATABASE_URL` | Адрес одноразовой базы CI; имя оканчивается на `_test` |
| `REQUIRE_TEST_DATABASE` | `1`: если адрес потерян, тесты базы падают, а не пропускаются |
| `DATABASE_URL` | Только для шагов Alembic; указывает на ту же тестовую базу |

Пароль `ci-only-password` записан в workflow открыто: он относится к
временному контейнеру без реальных данных, который удаляется после задания.
Для настоящих окружений пароли хранятся в секретах, а не в репозитории.

Шаги `alembic upgrade head` и `alembic check` проверяют миграцию из командной
строки. Затем `pytest` в начале сессии ещё раз удаляет и создаёт схему через
те же миграции и выполняет интеграционные тесты.

## Как повторить проверки локально

Из корня проекта:

```bash
uv sync --locked --group ui
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked --group ui mypy app tests scripts migrations ui sandbox
uv run --locked --group ui pytest
uv run --locked python scripts/check_docs.py
```

Без `TEST_DATABASE_URL` локальный `pytest` пропускает тесты PostgreSQL —
это видно в итоговой строке как `skipped`. Как подготовить базу и запустить
их, описано в [инструкции по тестам](instructions/testing.md).

Ожидаемый успешный результат — каждая команда завершается с кодом `0`.
Фактические выводы и число тестов фиксируются в
[VERIFICATION.md](VERIFICATION.md) и
[guide/verification.json](guide/verification.json).

Ruff и mypy не заменяют тесты, а тесты не заменяют проверку запущенного сервера.
Для сетевого запроса нужно отдельно запустить Uvicorn по
[инструкции](instructions/quickstart.md) и вызвать `/health` через `curl`.

## Конфигурация CI и подтверждённый запуск

Файл `.github/workflows/ci.yml` — инструкция для GitHub Actions. Его наличие
подтверждает конфигурацию, но не подтверждает, что GitHub действительно
запустил задание или что оно завершилось успешно.

Для проверки удалённого результата открой репозиторий на GitHub,
затем вкладку **Actions**. Выбери запуск workflow для нужного коммита
и посмотри результат всех шагов. В отчёт проверки записываются ссылка
на запуск и идентификатор коммита, для которого он выполнен.

Различай три факта:

1. **Настроено:** workflow существует и содержит нужные команды.
2. **Проверено локально:** команды выполнены на текущем компьютере.
3. **Подтверждено удалённо:** найден завершившийся запуск GitHub Actions
   для соответствующего коммита.

Статус `not_verified` означает, что удалённый результат не подтверждён.
Он не означает ни успешный, ни провалившийся запуск. Локальная зелёная
проверка не должна автоматически менять его на `passed`.

Документ не выполняет `git commit` или `git push`: фиксация и отправка
изменений — отдельные действия. После будущей отправки нужно проверить
результат, а не судить о нём только по наличию workflow.

## Что добавлять на следующих этапах

`pytest` в CI также выполняет `tests/test_guide_pdfs.py`: если код, миграции,
`uv.lock` или `verification.json` изменены без пересборки PDF-руководств, тест
падает. ReportLab для этого не нужен, поэтому CI не собирает PDF сам.

Тестовая БД и проверка миграций добавлены на этапе 03. На этапе 04 тот же
`pytest` запускает короткие подпроцессы Python для чтения PDF; дополнительный
сервис не нужен, а миграция `0002` применяется общими шагами Alembic.
Этапы 05, 06 и 07 тоже не требуют новых шагов: миграции `0003` и `0004`
применяются теми же командами (на этапе 07 — ещё `0005`), а тесты HTTP API
работают через `TestClient` без сетевого порта. Агент этапа 07 использует
только детерминированные провайдеры, поэтому CI не нужен ключ модели.
На этапе 08 CI ставит группу зависимостей `ui` (`uv sync --locked --group
ui`) и запускает mypy и pytest с ней: иначе тесты страницы Streamlit
пропускались бы. На этапе 09 mypy проверяет ещё пакет `sandbox`, миграция
`0006` применяется общими шагами, а весь набор оценок выполняется как тест
PostgreSQL (`tests/persistence/test_evals.py`); получатель webhook
запускается внутри тестового процесса на loopback, отдельный сервис не
нужен. Тест лимита памяти PDF-процесса выполняется только на Linux, то
есть именно в CI, — но удачный удалённый запуск пока не подтверждён. Сборка контейнера, публикация образа и развёртывание
добавляются вместе с соответствующим этапом. Каждый новый шаг должен
иметь понятную цель и проверяемый результат.
