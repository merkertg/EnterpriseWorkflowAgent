# PostgreSQL persistence

[README](../../README.md) · [Detailed Russian guide](../STAGE_03.md) ·
[ADR 0003](../adr/0003-postgresql-persistence-audit-idempotency.md) ·
[Verification](../VERIFICATION.md)

Stage 03 stores workflows in PostgreSQL with Alembic migrations, immutable input
versions, a transactional audit trail, optimistic locking and idempotent
commands. No new HTTP endpoints are added; `/health` does not check the database.

## Prepare databases

Use PostgreSQL 18 (verified with 18.3). Create a development database and a
separate test database whose name ends in `_test`:

```bash
createuser --pwprompt enterprise_workflow
createdb --owner enterprise_workflow enterprise_workflow
createdb --owner enterprise_workflow enterprise_workflow_test
```

Set the development URL in the environment or in your untracked `.env`:

```text
DATABASE_URL=postgresql+psycopg://enterprise_workflow:YOUR_PASSWORD@127.0.0.1:5432/enterprise_workflow
```

The `postgresql+psycopg://` driver prefix is required. The setting is a
`SecretStr`, so its password is hidden in settings representations. Engines use
a 5 s connect timeout, a 5 s lock timeout and a 30 s statement timeout.

## Migrate

```bash
uv run --locked alembic upgrade head
uv run --locked alembic current
uv run --locked alembic check
```

`alembic check` must print `No new upgrade operations detected`. Preview SQL
without connecting using `uv run --locked alembic upgrade head --sql`.
`alembic downgrade base` drops every Stage 03 table and its data.

Never edit an applied revision; add a new one. Revision `0001` was
autogenerated, then edited to add the circular workflow-to-snapshot foreign key
after both tables and to install append-only triggers.

## Run the demo

```bash
uv run --locked python -m app.persistence_demo
uv run --locked python -m app.persistence_demo show DEMO-WF-xxxxxxxxxxxx
```

The first command creates a fictional run with unique IDs and prints JSON:
start, check, an idempotent replay, a stale approval rejected with
`version_conflict`, new PO and policy versions, revise, a re-check needing
review and a rejection. `show` reads a stored workflow and its audit trail in a
new process. Exit code `2` means missing or invalid `DATABASE_URL`; `1` means a
connection, schema or command error.

## Use the service

```python
from app.application.ports import CommandContext
from app.infrastructure.db.session import build_workflow_service, create_database_engine

engine = create_database_engine(database_url)
service = build_workflow_service(engine)
invoice_v = service.record_invoice(invoice)
order_v = service.record_purchase_order(purchase_order)
policy_v = service.record_policy(policy)
service.start(
    "WF-1",
    invoice_version_id=invoice_v.version_id,
    purchase_order_version_id=order_v.version_id,
    policy_version_id=policy_v.version_id,
    context=CommandContext("a-new-uuid-per-intent", "my-script"),
)
service.check(
    "WF-1", expected_version=1, context=CommandContext("another-uuid", "my-script")
)
```

| Rule | Behavior |
| --- | --- |
| Input versions | Identical to the latest version → reused; different → next number; A → B → A creates version 3 |
| Content hash | SHA-256 of canonical JSON; recomputed on every load; a mismatch raises `StoredDataIntegrityError` |
| Pinned inputs | `start`/`revise` pin exact version IDs; `check` evaluates only the pinned versions |
| Transaction | Idempotency record, snapshot, workflow update and audit event commit together |
| Optimistic lock | `expected_version` must equal the stored version; also enforced by `UPDATE ... WHERE version = ...` |
| Idempotency | Same key and request → stored result with `replayed=True`; same key, other request → `IdempotencyKeyReusedError`; failed commands store nothing |
| Audit | IDs, command, states, versions, issue codes, caller-declared `actor_id` and `source`; no document text |
| History tables | Versions, snapshots, audit and idempotency rows reject `UPDATE`/`DELETE` via trigger |

Error codes: `not_found`, `workflow_exists`, `version_conflict`,
`idempotency_key_reused`, `stored_data_integrity`; domain errors keep their
Stage 02 codes such as `invalid_transition`.

## Limits

- `actor_id` and `source` are caller-declared. There is no authentication.
- A newer PO or policy version does not mark a pinned workflow stale and does
  not block approval yet; that is Stage 05 and Stage 06 work.
- Policy hashes cover policy data, not Python rule code. Changing rule logic
  needs a new policy ID; stored results produced by older logic fail to load.
- Triggers stop accidental edits. A database owner can still disable them.
- No backups, retention policy, multi-tenant isolation or HTTP commands.

For integration tests see [testing](testing.md).
