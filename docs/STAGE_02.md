# Этап 02. Предметная модель и правила процесса

[README](../README.md) · [Дорожная карта](ROADMAP.md) ·
[Проверка](VERIFICATION.md) · [Краткая инструкция на английском](instructions/domain.md)

## 1. Что делает этот этап

На этапе 01 приложение научилось запускаться и отвечать на `GET /health`.
Теперь добавляем сам предмет обучения: счёт поставщика, заказ на закупку,
денежные расчёты, проверку расхождений и допустимые переходы процесса.

**Предметная область** — часть реального рабочего процесса, которую описывает
программа. Здесь это проверка вымышленного счёта по вымышленному заказу на
закупку. Английское название заказа — *purchase order*, сокращённо **PO**.
Подтверждение фактического получения товара в этот сценарий не входит.

Этап 02 работает с Python-объектами в памяти. Данные создаются программой,
проверяются обычным кодом и исчезают после завершения процесса. Это основа
будущего приложения, а не законченный документооборот.

| Уже реализовано | Когда появится остальное |
| --- | --- |
| Модели счёта, заказа, позиции и денег | Сохранение и аудит — этап 03 |
| Базовые проверки ссылок, поставщика, валюты и итогов | Полная сверка позиций, допуски и версионные снимки — этап 05 |
| Состояния и команды процесса на уровне Python | Пользователи, роли и HTTP-команды согласования — этап 06 ([реализовано](STAGE_06.md)) |
| Локальная демонстрация на вымышленных данных | Загрузка файлов — этап 04; LLM — этап 07 |

Новых HTTP-маршрутов этот этап не добавляет. `/health` продолжает показывать
только способность API ответить на запрос. Одобрение в демонстрации означает
переход учебного объекта в состояние `approved`; платежей и обращений к
корпоративным системам нет.

## 2. Почему правила находятся отдельно от FastAPI

Счёт может поступить через HTTP, командную строку или будущий обработчик
документа. Во всех случаях сумма должна вычисляться одинаково, а запрещённый
переход должен отклоняться одинаково. Поэтому правила находятся в
`app/domain/` и используют стандартную библиотеку Python.

```text
Вымышленные Python-данные
    ↓
Money, LineItem, Invoice, PurchaseOrder
    ↓
Детерминированная проверка
    ↓
Структурированный результат с причинами
    ↓
Допустимая команда процесса
    ↓
Новый неизменяемый снимок состояния
```

**Детерминированная** функция при одинаковых аргументах возвращает одинаковый
результат. Ей не нужны сеть, база данных, текущее время или ответ модели.
Это позволяет отдельно проверить бизнес-правило и позднее вызывать его из
разных адаптеров.

Направление зависимости важно: HTTP-слой сможет импортировать доменные
функции, а домен не должен импортировать FastAPI, SQLAlchemy или SDK модели.
Архитектурное решение описано в
[ADR 0002](adr/0002-domain-rules-and-workflow.md).

## 3. Что такое неизменяемый объект

Модели представлены `dataclass` с `frozen=True`. `dataclass` добавляет
обычному Python-классу создание по полям и сравнение значений. `frozen=True`
запрещает обычное присваивание полю уже созданного объекта.

Позиции документа хранятся в `tuple`, то есть неизменяемой последовательности,
а не в изменяемом `list`. Это важно: запретить `invoice.lines = ...`
недостаточно, если внутри поля остаётся список, в который можно дописать
новую строку.

Изменение оформляется созданием нового объекта. Предыдущий снимок продолжает
описывать прежний ввод. Такое поведение делает проверки и переходы понятнее,
но само по себе не даёт хранения, аудита и защиты от параллельных изменений.
Эти задачи относятся к этапу 03.

## 4. Деньги: Decimal, валюта и округление

Обычный `float` хранит приближённое двоичное число. Для финансовых правил
нужно явное десятичное значение, поэтому домен принимает `Decimal`.
Создавай его из строки:

```python
from decimal import Decimal

price = Decimal("12.50")
quantity = Decimal("2")
```

Кавычки здесь важны. `Decimal(0.1)` получает уже приближённое значение
`float`. `Decimal("0.1")` получает точное десятичное значение. Конструктор
денег принимает именно `Decimal`: автоматического преобразования строки,
целого или `float` внутри домена нет. Преобразование внешнего ввода позднее
будет обязанностью адаптера.

Валюта хранится отдельно через `Currency`. На этом учебном этапе поддержаны
`USD`, `EUR` и `UZS`. Для **всех трёх** действует одно явно выбранное правило:
два десятичных знака и `ROUND_HALF_UP`. Это правило учебной модели; оно не
является каталогом всех валютных и бухгалтерских требований.

Входная цена и заявленная сумма должны быть точно представимы с двумя
десятичными знаками: `Decimal("1.00")` подходит, `Decimal("1.005")` вызывает
ошибку, а не молча исправляется. Незначащие нули допустимы:
`Decimal("1.000")` нормализуется в `1.00`.

Округление нужно **при умножении цены на количество**. `ROUND_HALF_UP`
означает округление ближайшего значения с увеличением при точной половине:
цена `0.01` × количество `0.5` даёт `0.005`, итог позиции округляется до
`0.01`. Сначала округляется каждая позиция, затем складываются её итоги.
Две такие позиции дадут `0.02`, хотя округление общей исходной суммы дало бы
`0.01`. Важен именно выбранный порядок вычислений.

Ограничения этого этапа:

| Значение | Ограничение |
| --- | --- |
| Сумма денег | Конечное неотрицательное `Decimal`, не больше `999999999999.99`, точно представимое с двумя десятичными знаками |
| Количество | Конечное положительное `Decimal`, максимум `999999.999999`, точно представимое не более чем с шестью десятичными знаками |
| Валюта | Явное значение `Currency`; автоматической конвертации нет |
| Позиции документа | От 1 до 100, без повторяющихся SKU |

`NaN` означает «не число», `Infinity` — бесконечность. Они допустимы как
некоторые значения `Decimal`, но не являются допустимой суммой или количеством
в этом проекте. Отрицательная цена также не подходит. Возвраты, скидки,
налоги и валютная конвертация отдельными правилами здесь не моделируются.

Вычисления используют отдельный десятичный контекст с заданными точностью
и округлением. Изменение глобального контекста `Decimal` в другом участке
программы не должно менять доменные итоги. Слишком большой итог позиции или
документа тоже отклоняется, даже если каждая отдельная цена укладывалась
в разрешённый предел.

## 5. Позиция, счёт и заказ

**SKU** — идентификатор позиции товара или услуги. Для примера можно взять
вымышленный код `DEMO-SERVICE`. Это код позиции, а не её описание.

| Объект | Поля и смысл |
| --- | --- |
| `LineItem` | `sku`, `description`, `quantity`, `unit_price`: код, описание, количество и цена единицы |
| `Invoice` | `invoice_id`, `supplier_id`, `purchase_order_id`, `currency`, `lines`, `declared_total`: счёт, поставщик, ссылка на заказ, валюта, позиции и заявленный итог |
| `PurchaseOrder` | `purchase_order_id`, `supplier_id`, `currency`, `lines`: заказ, поставщик, валюта и позиции |

Идентификаторы обязательны и не должны быть пустыми. Пробелы по краям
удаляются. Максимальная длина обычного идентификатора — 128 символов,
описания позиции — 500 символов. Все позиции одного
документа должны соответствовать его валюте. `declared_total` хранит сумму,
которую указал поставщик; программа независимо рассчитывает итог по позициям.
Эти значения нужны отдельно, чтобы ошибка в заявленном итоге была обнаружима.

Некорректное представление и допустимое представление с расхождением — разные
ситуации. Отрицательное количество не образует корректную позицию и
отклоняется при создании. Корректный счёт с другим поставщиком может быть
создан, но проверка вернёт причину для ручного разбора.

## 6. Как читать результат проверки

`evaluate_invoice(invoice, purchase_order, policy=None)` принимает счёт,
заказ или `None` и необязательную явную политику проверки. Отсутствующий
заказ обозначается `None`. Если политика не передана, создаётся
`ValidationPolicy()` с `policy_id="basic-demo-v1"` и разрешёнными валютами
`USD`, `EUR`, `UZS`. Можно передать политику с меньшим набором валют.
Идентификатор политики — метка этого учебного правила; хешей и сохранённых
в БД версий политики на этапе 02 нет.

`ValidationResult` содержит точные неизменяемые входы `invoice`,
`purchase_order`, `policy`, набор `issues` и свойства `is_valid`,
`calculated_total`. Это снимок объектов в памяти, а не архив документа.
`is_valid=True` означает, что набор причин пуст.

Начальные правила проверяют:

| Код `IssueCode` | Что означает |
| --- | --- |
| `unsupported_currency` | Валюта корректного счёта не входит в разрешённый набор политики |
| `invoice_total_mismatch` | Заявленный итог не совпадает с суммой округлённых позиций |
| `missing_purchase_order` | Заказ не предоставлен |
| `purchase_order_reference_mismatch` | Ссылка счёта не совпадает с идентификатором переданного заказа |
| `supplier_mismatch` | Поставщик счёта отличается от поставщика заказа |
| `currency_mismatch` | Валюта счёта отличается от валюты заказа |
| `purchase_order_total_exceeded` | Заявленный итог счёта превышает итог заказа в той же валюте |

Причины возвращаются в стабильном порядке таблицы. При отсутствии заказа
проверка всё ещё проверяет политику валюты и собственный итог счёта, затем
возвращает `missing_purchase_order`: сравнивать с отсутствующим заказом нечего.
При разных валютах сравнение сумм не выполняется.

Одна ошибка может дать несколько причин. Если сумма позиций равна `30.00`,
заявлено `31.00`, а итог заказа равен `30.00`, появятся одновременно
`invoice_total_mismatch` и `purchase_order_total_exceeded`.

Каждый `RuleIssue` хранит `code`, `field`, `message` и, где применимо,
`expected`, `actual`: ожидаемое и фактическое значение. Код причины нужен
программе: по нему можно написать тест и позднее выбрать
текст интерфейса. Сообщение помогает человеку понять причину. Нельзя
подменять проверку поиском отдельного слова в сообщении: формулировка может
поменяться, а смысл кода должен оставаться явным.

Отсутствие причин означает только прохождение **этих начальных правил**.
На этапе 02 ещё нет полного сопоставления каждой позиции счёта с позицией
заказа. Например, одинаковый общий итог сам по себе не доказывает совпадение
SKU, количества и цены. Полную сверку с допусками и воспроизводимыми версиями
входов добавит этап 05.

## 7. Состояния и переходы

**Состояние** описывает положение счёта в учебном процессе. **Команда** —
явная просьба выполнить действие. Команда может быть отклонена, если её
условия не выполнены.

| Состояние | Значение |
| --- | --- |
| `received` | Данные получены и готовы к проверке |
| `needs_review` | Найдены причины для ручного разбора |
| `awaiting_approval` | Начальные правила пройдены, можно передать решение человеку |
| `approved` | Явное решение об одобрении записано в доменном снимке |
| `rejected` | Явное решение об отклонении записано в доменном снимке |

Проверка не переводит счёт напрямую в `approved`. Даже чистый результат
означает только `awaiting_approval`. Одобрение требует отдельной команды и
данных о человеке, принявшем решение.

`HumanDecision` содержит `actor_id` и `reason`: идентификатор действующего
лица и причину. На этапе 02 это значения, переданные вызывающим кодом.
Само наличие строки `actor_id` не подтверждает личность и полномочия.
Серверная идентификация и проверка ролей появились на
[этапе 06](STAGE_06.md); на этапе 02 команды доступны только как локальные
Python-функции.

`approved` и `rejected` — конечные состояния текущей модели. После них
нельзя повторно проверять, одобрять, отклонять или заменять документ в том же
процессе. Повтор команды не считается успешным новым решением.

| Функция | Исходное состояние | Условие и результат |
| --- | --- | --- |
| `check_workflow(workflow)` | Любое незавершённое | Чистая проверка → `awaiting_approval`; причины → `needs_review` |
| `approve_workflow(workflow, decision)` | Только `awaiting_approval` | Свежая чистая проверка совпадает с сохранённой; явное решение → `approved` |
| `reject_workflow(workflow, decision)` | Любое незавершённое | Явное решение с причиной → `rejected`, проверка заранее не обязательна |
| `revise_workflow(workflow, invoice, purchase_order, *, policy=None)` | Любое незавершённое | Новый снимок того же `invoice_id` → `received`, прошлые проверка и решение сняты |

Незавершёнными здесь являются `received`, `needs_review` и
`awaiting_approval`. У `HumanDecision` обязательны оба непустых поля;
максимальная длина причины — 2000 символов.

Перед одобрением правило проверяется заново на актуальных переданных
входах. Это защищает учебную команду от использования старого результата
после смены входных данных. Проверка в памяти не является транзакцией БД
и не решает конкурентные изменения между разными процессами.

Исправление возвращает незавершённый процесс в `received` и снимает прежний
результат проверки: изменённые данные должны пройти проверку заново.

Аргумент `purchase_order` у `revise_workflow()` обязателен: передать `None`
означает сознательно убрать заказ. `policy=None` сохраняет действующую
политику, а явная политика заменяет её. Подменить `invoice_id` при исправлении
нельзя: другой счёт требует другого процесса.

Конструктор `Workflow` также проверяет согласованность полей. Нельзя создать
`awaiting_approval` без чистого результата, `approved` без решения или
приложить устаревшие либо придуманные причины к текущим входам.

## 8. Пример вызова из Python

Следующий код можно сохранить во временный файл в корне проекта и запустить
через `uv run --locked python имя_файла.py`, либо выполнить в интерпретаторе
после `uv run --locked python`:

```python
from decimal import Decimal

from app.domain.models import Invoice, LineItem, PurchaseOrder
from app.domain.money import Currency, Money
from app.domain.workflow import (
    HumanDecision,
    Workflow,
    approve_workflow,
    check_workflow,
)

line = LineItem(
    sku="DEMO-SERVICE",
    description="Fictional support session",
    quantity=Decimal("2"),
    unit_price=Money(amount=Decimal("15.00"), currency=Currency.USD),
)
order = PurchaseOrder(
    purchase_order_id="DEMO-PO-001",
    supplier_id="demo-supplier",
    currency=Currency.USD,
    lines=(line,),
)
invoice = Invoice(
    invoice_id="DEMO-INV-001",
    supplier_id="demo-supplier",
    purchase_order_id="DEMO-PO-001",
    currency=Currency.USD,
    lines=(line,),
    declared_total=Money(amount=Decimal("30.00"), currency=Currency.USD),
)
received = Workflow(
    workflow_id="DEMO-WF-001",
    invoice=invoice,
    purchase_order=order,
)
checked = check_workflow(workflow=received)
approved = approve_workflow(
    workflow=checked,
    decision=HumanDecision(
        actor_id="demo-approver-1",
        reason="Fictional learning example reviewed",
    ),
)
print(received.state.value)  # received
print(checked.state.value)  # awaiting_approval
print(approved.state.value)  # approved
```

Обрати внимание на `(line,)`: запятая создаёт `tuple` из одного элемента.
`(line)` только заключает объект в скобки и не образует последовательность.
Пример использует один неизменяемый объект позиции для двух вымышленных
документов. Это безопасно благодаря неизменяемости; в реальном извлечении
данных счёт и заказ будут создавать собственные позиции.

Переменная `received` после одобрения всё ещё имеет состояние `received`.
Команды вернули новые снимки `checked` и `approved`, а не изменили прошлые.

## 9. Локальная демонстрация

Из корня проекта выполни:

```bash
uv sync --locked
uv run --locked python -m app.demo
```

Демонстрация создаёт вымышленные данные внутри программы и выводит JSON.
Она показывает случаи:

- Согласованные данные проходят начальную проверку, после явного решения
  получается `approved`.
- Расхождение приводит к `needs_review` и содержит причины, которые нужно
  разобрать человеку.
- Отсутствующий заказ явно отражается кодом `missing_purchase_order`.

Для этой команды не нужен запущенный Uvicorn, файл `.env`, API-ключ или база
данных. Это прямой вызов Python-функций, поэтому он не добавляет в `/docs`
команды согласования. Повтор запуска создаёт новый независимый пример.

Если команда завершилась без ошибки, это подтверждает запуск конкретной
демонстрации. Тесты проверяют больше ситуаций, а фактические результаты
запусков находятся в [отчёте проверки](VERIFICATION.md).

| Файл | Для чего читать |
| --- | --- |
| `app/domain/errors.py` | Какие ошибки обозначают недопустимый ввод и команду |

| `app/domain/workflow.py` | Состояния, решение человека и разрешённые команды |
| `app/demo.py` | Полный локальный пример без сети и внешних действий |
| `tests/` | Проверки нормальных, пограничных и запрещённых сценариев |

**Инвариант** — условие, которое обязано сохраняться для корректного объекта.
Например, количество положительно, цена соответствует валюте документа,
а набор позиций не содержит одинаковый SKU. Проверка инвариантов при создании
не позволяет случайно передать дальше заведомо некорректный объект.

Начинай чтение с `app/demo.py`: сначала видно, какую задачу выполняет
программа. Затем переходи в `models.py`, `money.py`, `rules.py` и
`workflow.py`, сопоставляя каждый вызов демонстрации с его реализацией.

## 11. Как проверять этап

Команды выполняются из корня проекта:

```bash
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked pytest
uv run --locked python scripts/check_docs.py
uv run --locked python -m app.demo
```

Ruff проверяет оформление и типичные ошибки. mypy проверяет согласованность
аннотаций типов, но не вычисляет правильность всех бизнес-условий. pytest
проверяет конкретное поведение, включая запрещённые входы и переходы.
Проверка ссылок помогает не направлять читателя в отсутствующие локальные
файлы. Внешние URL и содержание ссылок она не подтверждает.

Обрати внимание на отрицательные сценарии: другая валюта, отрицательная
сумма, пустые позиции, повтор SKU, несоответствие поставщика, отсутствие заказа,
одобрение без проверки и повторное решение после конечного состояния.
Проверка отказа так же важна, как проверка успешного примера.

Точное число тестов и выполненные команды указаны в
[VERIFICATION.md](VERIFICATION.md) и
[guide/verification.json](guide/verification.json). Локальные проверки,
демонстрация, реальный вызов модели и удалённый CI фиксируются отдельно.
Наличие workflow-файла не означает, что GitHub Actions запускался.

## 12. Типичные затруднения

| Симптом | Причина и действие |
| --- | --- |
| Деньги не создаются из `12.50` или `"12.50"` | Нужен явный `Decimal("12.50")`; домен не угадывает тип входа |
| Деньги не создаются из `Decimal("1.005")` | Вход обязан быть точно представим в сотых; HALF_UP применяется к произведению цены и количества |
| Не принимается строка валюты | Передай значение `Currency`, чтобы валюта была явной |
| Количество `0` отклонено | Позиция должна содержать положительное количество |
| Повтор SKU отклонён | В этом этапе один SKU встречается один раз в документе |
| Чистая проверка не дала `approved` | Сначала получается `awaiting_approval`; решение человека — отдельная команда |
| `actor_id` заполнен, но HTTP-команды нет | Строка идентификатора ещё не является аутентификацией; это задача этапа 06 |
| Изменение атрибута не работает | Создай новый объект и используй команду исправления |
| После исправления снова `received` | Старый результат больше не применим, нужна повторная проверка |
| После перезапуска данных нет | Этап работает в памяти; хранение появится на этапе 03 |
| Все итоги совпали, но нужна сверка SKU | Полная построчная сверка запланирована на этапе 05 |

## 13. Вопросы после разбора

Сначала прочитай код и запусти демонстрацию, затем попробуй объяснить:

1. Почему заявленный итог хранится отдельно от рассчитанного?
2. Зачем передавать `Decimal("0.1")`, а не `Decimal(0.1)`?
3. Почему деньги должны содержать валюту?
4. Чем ошибочный вход отличается от расхождения в корректных документах?
5. Почему позиции хранятся в `tuple`, если модель уже `frozen=True`?
6. Почему чистая проверка приводит к ожиданию решения человека?
7. Что гарантирует повторная проверка перед одобрением, а что пока не
   гарантируется без БД и транзакций?
8. Почему `actor_id="employee-1"` не подтверждает полномочия?
9. Почему одинаковая общая сумма ещё не доказывает совпадение позиций?
10. Что именно сохраняется после функции перехода и что произойдёт после
    завершения процесса Python?

Следующий этап добавит PostgreSQL, миграции, транзакции и аудит. Домен останется
обычным Python-кодом: база данных будет сохранять его результат, а не определять
его правила.
